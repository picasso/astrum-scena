# Gallery

- **Статус контракта:** согласован
- **Обновлено:** 2026-08-26
- **Общие правила:** [контентные блоки](README.md)

## Назначение

`Gallery` вставляет в текст полноширинную полосу изображений одинаковой визуальной высоты. Галерея
может показывать явный список изображений, содержимое альбома или составной именованный набор. При
необходимости она выбирает новый случайный состав при каждом отображении страницы и не загружает
изображения до приближения к области видимости.

Основные визуальные примеры — две галереи на
странице About исходного сайта: прямоугольная динамическая полоса после
первого фрагмента текста и квадратная динамическая галерея ниже. Первая legacy-галерея занимает всю
ширину контентной колонки, показывает три снимка на широком контейнере и только первый на телефоне.

Блок не предназначен для:

- masonry-раскладки с неровным нижним краем;
- колонок естественных изображений разной высоты;
- слайдера или полноэкранного hero;
- загрузки изображений по внешнему URL;
- произвольной HTML/CSS-композиции и авторских классов.

## Что найдено в исходном контенте

Обе галереи About остались шорткодами, а не сохранёнными Gutenberg-блоками:

```text
[gallery kind="lazyload" gutters="1" aclick="lightbox" randset="true" albums="6"
  size="medium" bordered="thin" ids="383" classes="mobile-firstonly"]

[gallery kind="square" gutters="1" aclick="lightbox" randset="true" albums="30"
  size="medium" bordered="small" ids="383"]
```

Фактическое поведение первой галереи подтверждает отложенную загрузку: до приближения к viewport у
`img` нет рабочего `src`, затем responsive-источник назначается JavaScript. Повторная загрузка
legacy-страницы может вернуть тот же набор из серверного кэша. Новый контракт сознательно меняет
этот аспект: случайный состав вычисляется в браузере при каждом отображении страницы и поэтому не
зависит от частоты сборок или серверного кэша.

Шорткод нужен как источник фактического поведения страницы, но его API не восстанавливается.
Публичный контракт ниже основан на согласованных редакторских требованиях, актуальных Gutenberg-
атрибутах и нормализованной модели управляемых изображений.

## Основные решения

- Существует один блок `Gallery`, а не отдельные `Gallery` и `LazyGallery`.
- Lazy loading обязателен для всех типов и не является публичным параметром.
- По умолчанию галерея занимает 100% фактической ширины контейнера контента; `outside` может
  симметрично расширить её в свободные боковые поля.
- Поддерживаются только `rect`, `square` и `justified`: все они дают ровную полосу без дырок разной
  высоты.
- Динамика выполняется при отображении страницы, а не при сборке.
- Все источники состоят только из управляемых идентификаторов.
- Адаптивность обязательна и автоматически следует ширине контейнера.

## Публичный контракт

```ts
type GalleryLayout = 'rect' | 'square' | 'justified'
type GalleryColumns = 1 | 2 | 3 | 4 | 5
type GalleryGap = 'none' | 'tiny' | 'small' | 'medium' | 'large'
type ImageFrame = 'none' | 'thin' | 'medium' | 'thick'
type ImageFrameColor = 'default' | 'alt'
type LightboxScope = 'block' | 'page'

type FocalPoint = {
	x: number
	y: number
}

type ImageAction =
	| 'none'
	| 'lightbox'
	| 'photo'
	| { type: 'album'; albumId: string }
	| { type: 'custom'; href: string; newTab?: boolean }

type GalleryImageOverrides = {
	imageId: string
	alt?: string
	caption?: string | false
	action?: ImageAction
	focalPoint?: FocalPoint
}

type GalleryImage = string | GalleryImageOverrides

type GalleryProps = {
	imageSetId?: string
	albumId?: string
	images?: GalleryImage[]
	exclude?: string[]
	randomCount?: number
	layout?: GalleryLayout
	columns?: GalleryColumns
	outside?: number
	mobileFirstOnly?: boolean
	gap?: GalleryGap
	frame?: ImageFrame
	frameColor?: ImageFrameColor
	action?: ImageAction
	inlineCaption?: boolean
	lightboxCaption?: boolean
	lightboxScope?: LightboxScope
}
```

Короткая строковая запись изображения эквивалентна `{ imageId: value }`. Объект нужен только для
локальных overrides.

| Параметр          | Default      | Правило                                                                   |
| ----------------- | ------------ | ------------------------------------------------------------------------- |
| `imageSetId`      | —            | Именованный составной набор; источник с наивысшим приоритетом             |
| `albumId`         | —            | Все изображения управляемого альбома; второй приоритет                    |
| `images`          | —            | Явный непустой список; третий приоритет                                   |
| `exclude`         | `[]`         | Управляемые IDs, удаляемые из выбранного источника до фильтрации и random |
| `randomCount`     | отсутствует  | Положительное целое число уникальных случайных изображений                |
| `layout`          | `'rect'`     | `rect`, `square` или `justified`                                          |
| `columns`         | `3`          | Максимальная плотность: точное число ячеек либо цель для justified        |
| `outside`         | `0`          | Целый breakout `0..60` на каждую сторону prose                            |
| `mobileFirstOnly` | `true`       | На телефоне показывать только первый элемент выбранного состава           |
| `gap`             | `'small'`    | Единый горизонтальный и вертикальный межэлементный токен                  |
| `frame`           | `'thin'`     | Рамка каждой ячейки: `none`, `thin`, `medium` или `thick`                 |
| `frameColor`      | `'default'`  | Сайт-токен `default` или `alt`; не влияет при `frame='none'`              |
| `action`          | `'lightbox'` | Общее действие; явный элемент `images` может переопределить               |
| `inlineCaption`   | `false`      | Показывать разрешённые подписи поверх превью                              |
| `lightboxCaption` | `true`       | Передавать разрешённые подписи в lightbox                                 |
| `lightboxScope`   | `'page'`     | Общая совместимая группа страницы или изолированная группа блока          |

Хотя API допускает присутствие нескольких источников для безопасного приёма мигрированного
контента, хотя бы один из `imageSetId`, `albumId` или `images` обязателен. Приоритет строго такой:

```text
imageSetId > albumId > images
```

Неизвестный источник верхнего уровня является ошибкой и не разрешает молча перейти к следующему.
Если несколько известных источников заданы одновременно, верхний используется, а сборка сообщает о
проигнорированных нижних параметрах. Это позволяет обнаружить лишние данные, сохраняя однозначный
результат.

Произвольные `className`, `width`, `align`, внешний `src`, готовые `srcset`/`sizes`, loader, delay,
hover-эффекты и ручные responsive-флаги в публичный контракт не входят.

## Примеры авторинга

Динамическая прямоугольная полоса из именованного пула:

```mdx
<Gallery imageSetId="about-intro" randomCount={3} />
```

Квадратная галерея из альбома:

```mdx
<Gallery albumId="amazing-japan" randomCount={6} layout="square" columns={3} />
```

Центрированная justified-галерея с выходом за prose на 20% его ширины с каждой стороны:

```mdx
<Gallery albumId="sunrises-for" layout="justified" columns={3} outside={20} />
```

Явный редакторский список с overrides:

```mdx
<Gallery
	layout="justified"
	images={[
		'symmetry-of-sound',
		{
			imageId: 'divine-light',
			caption: false,
			action: { type: 'album', albumId: 'iceland' },
		},
		{
			imageId: 'dr-bhutan',
			alt: '',
			focalPoint: { x: 42.5, y: 30 },
		},
	]}
/>
```

`focalPoint` в последнем примере сохраняется как override вхождения, но визуально используется
только при переходе этого блока на `rect` или `square`.

## Именованные наборы изображений

Именованные наборы хранятся в одном плоском ручном справочнике:

```text
src/content/config/image-sets.yaml
```

Набор является внутренним пулом, а не публичным альбомом: у него нет страницы, названия, описания,
обложки или локализации. RU и EN используют один пул, но независимо делают случайную выборку и не
обязаны показывать одинаковый состав.

```yaml
schemaVersion: 1
about-intro:
    albumIds:
        - sunrises-for
        - iceland
    photoIds:
        - symmetry-of-sound
        - divine-light
        - volterra-fog
    priorityPhotoIds:
        - divine-light
    order: favorites-first
```

Исполняемый контракт справочника:

```ts
type ImageSetOrder =
	| 'source'
	| 'favorites-first'
	| 'published-newest'
	| 'published-oldest'
	| 'captured-newest'
	| 'captured-oldest'

type ImageSet = {
	albumIds?: string[]
	photoIds?: string[]
	priorityPhotoIds?: string[]
	order?: ImageSetOrder
}
```

ID набора — стабильный `kebab-case`. Хотя бы один из `albumIds` или `photoIds` должен быть непустым.
Все списки содержат уникальные управляемые IDs. Неизвестные альбомы и изображения, а также
неопубликованные или недоступные для встраивания элементы являются ошибкой конфигурации. `unlisted`
не означает запрет встраивания: такое опубликованное изображение допустимо в явном управляемом
наборе.

### Раскрытие и удаление повторов

Канонический исходный порядок строится так:

1. Альбомы обходятся в порядке `albumIds`.
2. Каждый альбом раскрывается в порядке его `photoIds`.
3. Прямые изображения добавляются после альбомов в порядке `photoIds` набора.
4. Если ID встретился в двух альбомах или одновременно в альбоме и прямом списке, сохраняется только
   первое вхождение.

Таким образом, два альбома и три отдельных изображения образуют один общий пул без копирования
метаданных фотографий.

### Сортировка и ручной приоритет

`order` управляет каноническим порядком раскрытого набора и по умолчанию равен `source`:

- `source` сохраняет описанный выше порядок;
- `favorites-first` сначала ставит `favorite: true`, сохраняя исходный порядок внутри обеих групп;
- `published-newest` и `published-oldest` используют дату появления фотографии на новом сайте;
- `captured-newest` и `captured-oldest` используют подтверждённые год или год-месяц съёмки.

При одинаковом значении сохраняется исходный порядок. При сортировке по `capturedAt` элементы без
даты всегда идут в конце независимо от направления.

После автоматической сортировки `priorityPhotoIds` поднимаются наверх в указанном порядке. Остальные
элементы сохраняют порядок, рассчитанный через `order`. При включённом random приоритет применяется
только к уже выбранному составу: он не гарантирует попадание изображения и не повышает вероятность
выбора.

Каждый `priorityPhotoIds` обязан уже присутствовать в пуле, полученном после раскрытия
`albumIds + photoIds`. Неизвестный или отсутствующий в пуле ID является ошибкой конфигурации:
`priorityPhotoIds` только меняет порядок и не добавляет изображения неявно.

`order` и `priorityPhotoIds` существуют только у именованного набора. Явный `images` уже задаёт
редакторский порядок, а `albumId` использует канонический порядок альбома. Если альбом нужен в другой
сортировке, для него создаётся image set.

### Размер пула и HTML

Жёсткого ограничения на размер image set нет. При этом весь пул динамической галереи попадает в
инертный `<template>`, поэтому большой набор увеличивает HTML страницы, хотя файлы невыбранных
изображений не загружаются.

Ориентир для текущего image pipeline с responsive-превью и данными PhotoSwipe:

- один кандидат занимает около `1,6–1,8 КБ` несжатого HTML;
- `<template>` из 20 кандидатов — около `35 КБ`;
- `<noscript>` для трёх изображений добавляет около `5 КБ`;
- итоговые дополнительные `40 КБ` превращаются примерно в `7–10 КБ` при передаче с Brotli/Gzip.

Цифры зависят от количества responsive-ширин, действия и длины подписей. Пулы из десятков
изображений считаются нормальными. Если на одном из сайтов появятся регулярные пулы из сотен
изображений, внутреннюю передачу кандидатов можно заменить отдельной статической проекцией без
изменения `Gallery` или формата image set. Авторский лимит для этого не вводится.

## Разрешение источника и конвейер выборки

Сборка и клиент должны применять операции в определённом порядке:

1. Выбрать источник по приоритету `imageSetId > albumId > images`.
2. Раскрыть альбомы набора и удалить повторные IDs с сохранением первого вхождения.
3. Удалить явный `exclude`.
4. Для динамического `rect` оставить только изображения с `width / height >= 4 / 3`.
5. Проверить, что после постоянных фильтров пул содержит не меньше `randomCount` элементов.
6. При наличии `randomCount` равновероятно выбрать указанное число уникальных IDs.
7. Для image set расположить выбранные элементы согласно `priorityPhotoIds` и `order`.
8. На сборке разрешить метаданные, действия, подписи и responsive-производные всех оставшихся
   кандидатов; в живой DOM материализовать только итоговый клиентский состав.

Шаг 4 применяется только к случайному `rect`. Явный неслучайный список является редакторским
решением и не фильтруется по ориентации. `square` может обрезать горизонтальные и вертикальные
изображения, а `justified` сохраняет естественное соотношение сторон.

`exclude` работает одинаково для всех трёх источников. Он содержит только управляемые ID;
неизвестный ID считается ошибкой. После исключений и layout-фильтра недостаточный постоянный пул —
ошибка сборки, а не уменьшение количества элементов.

## Динамический random

`randomCount` — положительное целое число. Его отсутствие означает вывод всего пула в каноническом
порядке без случайной выборки.

Случайная выборка должна быть честной:

- выполняется в браузере при каждом отображении страницы;
- не использует seed, local storage или session storage;
- не пытается насильно отличаться от предыдущего просмотра;
- допускает случайное повторение прежнего состава;
- не синхронизируется между RU и EN;
- не зависит от новой сборки сайта и не требует Pages Function.

Внутри одного блока повторов быть не может. Алгоритм должен делать равновероятную выборку без
возврата; подходящая реализация — корректный Fisher–Yates shuffle или эквивалентная unbiased sample.
Тесты используют внедряемый источник случайности, но production не получает редакторский seed.

### Исключение повторов между галереями страницы

Динамические галереи координируются на уровне текущего документа:

1. Обрабатываются в DOM-порядке.
2. IDs, выбранные предыдущими галереями, временно исключаются из следующих.
3. Если уникальных кандидатов достаточно, одна фотография не появляется в двух динамических
   галереях одной страницы.
4. Если после межгалерейного исключения кандидатов недостаточно, следующая галерея может повторно
   использовать ранее показанные IDs, чтобы сохранить свой `randomCount`.
5. Даже при таком fallback внутри самой галереи повторов нет.

Это best-effort правило только текущего отображения страницы. Оно не записывает состояние между
визитами и не превращает нехватку из-за предыдущей галереи в ошибку. Явный `exclude` остаётся
жёстким: элементы из него нельзя вернуть для заполнения.

Выбранный состав сохраняется на время жизни страницы. Изменение ширины контейнера или поворот
устройства не запускают новый random.

## Layout

### `rect`

- Каждая ячейка имеет фиксированное соотношение `3:2`.
- Изображение заполняет ячейку через `object-fit: cover`.
- Автоматический random использует только исходники с `width / height >= 4 / 3`, чтобы не получать
  чрезмерный вертикальный кроп.
- Обрезанное превью открывается в lightbox через `fade`.

Порог `4:3` — нормализованное новое правило. Legacy-плагин приблизительно проверял отношение
`width / height > 1.35` через допуск около эталона `3:2`; переносить эту неочевидную погрешность нет
необходимости.

### `square`

- Каждая ячейка имеет фиксированное соотношение `1:1`.
- Изображение заполняет ячейку через `object-fit: cover`.
- Допустимы все ориентации.
- Обрезанное превью открывается в lightbox через `fade`.

### `justified`

- Изображение не обрезается и сохраняет естественное соотношение сторон.
- Все элементы одной строки получают одинаковую вычисленную высоту.
- `columns` задаёт целевую плотность, а не точное количество элементов в каждой строке.
- Высота строки рассчитывается автоматически из ширины контейнера, gaps, рамок и aspect ratios.
- Последняя неполная строка использует `nojustify`: не растягивается до правого края и выравнивается
  по началу строки.
- Natural preview использует стандартную open animation сайта.

Публичного параметра ratio или row height нет. Целевая высота вычисляется по итоговому выбранному
составу:

```text
effectiveColumns =
  min(columns, max(1, floor((containerWidth + gap) / (240px + gap))))

availableWidth =
  containerWidth - gap * (effectiveColumns - 1) - frame * 2 * effectiveColumns

averageAspectRatio = mean(imageWidth / imageHeight)

averageCellWidth = availableWidth / effectiveColumns

targetRowHeight = averageCellWidth / averageAspectRatio
```

`frame` в формуле означает числовую толщину выбранной рамки. Например, для контейнера `680px`,
трёх целевых колонок, `gap=8px` и стандартной рамки `1px` преимущественно горизонтальные изображения
`3:2` дают целевую высоту около `146px`, квадратные — около `219px`, вертикальные `2:3` — около
`329px`. Смешанный состав использует среднее отношение сторон.

После определения target алгоритм набирает изображения в строку и корректирует её общую высоту,
чтобы все элементы строки заполнили контейнер без кропа и искажения. Высота может немного меняться
между загрузками вместе со случайным составом — это часть динамического поведения. Последняя строка
остаётся natural `nojustify`.

### Исключённые раскладки

`masonry` не поддерживается: при разных высотах он оставляет неровную композицию и визуальные
провалы в полосе, разрывающей текст. По той же причине не поддерживается natural `columns` с
одинаковой шириной и разной высотой изображений.

## Адаптивность

`columns` задаёт максимум от 1 до 5:

- для `rect` и `square` это максимальное точное количество ячеек в строке;
- для `justified` это целевая плотность, влияющая на автоматическую высоту строки.

Фактическая плотность может автоматически уменьшаться, когда контейнер становится слишком узким.
Решение принимается по ширине контейнера блока, а не viewport. Публичного `adaptive` нет: поддержка
разных размеров обязательна и не может быть выключена редактором.

Для всех раскладок Gallery минимальная практическая ширина плитки равна `240px`. Это общий порог
визуальной плотности: он не даёт трём колонкам держаться до слишком узкой полосы, а двум —
переключаться в одну почти сразу. Для `rect` и `square` он задаёт минимальную ширину CSS-плитки.
Фактическое количество колонок
вычисляется с учётом текущего gap:

```text
actualColumns = min(columns, floor((containerWidth + gap) / (240px + gap)))
```

Результат ограничивается снизу одной колонкой. Например, при `gap=8px` контейнер `680px` вмещает
две плитки примерно по `336px`; три колонки становятся доступны от `736px`, а одна остаётся ниже
`488px`. Для `justified` ориентир `240px` уменьшает только `effectiveColumns`; это не
жёсткий минимум отдельной natural-ячейки, ширина которой следует aspect ratio и вычисленной высоте
строки.

При `mobileFirstOnly=true` телефон показывает только первый элемент уже выбранного desktop-состава.
Остальные элементы не должны загружаться. Если контейнер затем становится шире, открывается тот же
ранее выбранный состав без нового random. `mobileFirstOnly=false` разрешает автоматической сетке
показать столько элементов, сколько помещается безопасно.

Телефонный режим включается при ширине контейнера `<= 480px`. Это container boundary, а не проверка
типа устройства или ширины всего viewport: тот же блок ведёт себя одинаково в любой узкой области
страницы. Значение не является MDX-параметром.

### Выход за prose (`outside`)

`outside` — целое число от `0` до `60`, задающее выход **на каждую сторону** prose в процентных
пунктах её ширины. Например, при prose `648px` и `outside={20}` желаемая ширина полосы равна
`648px + 2 × 129.6px = 907.2px`: галерея остаётся центрированной и расширяется одинаково влево и
вправо. Одностороннего варианта и параметра `position` нет.

Фактический выход ограничивается свободным местом между границей prose и безопасным padding viewport:

```text
outsideAvailable = max(0, 50vw - 50cqw - containerPad)
outsideEffective = min(outside × 1cqw, outsideAvailable)
galleryWidth = proseWidth + 2 × outsideEffective
```

Поэтому полоса никогда не создаёт горизонтальный scroll. При сужении viewport она плавно возвращается
к ширине prose; при prose `<= 480px` выход принудительно равен нулю. `mobileFirstOnly` использует
ширину prose до breakout, чтобы расширенная полоса не выключала телефонное состояние преждевременно.

Расширенная ширина является фактической шириной раскладки: `rect` и `square` выбирают число колонок
по ней, а `justified` заново упаковывает строки через существующий `ResizeObserver`. Текущий `sizes`
контракт Gallery уже ограничен верхней оценкой full-width surface и потолком `galleryCell` в 800 px,
поэтому отдельного author-facing responsive-параметра не требуется.

## Рамки и расстояния

`gap` использует [общую шкалу контентных блоков](README.md#общая-шкала-расстояний): `none`, `tiny`,
`small`, `medium`, `large` (`0/4/8/12/16 px` на текущем сайте). Одно значение управляет
горизонтальными и вертикальными расстояниями. Раздельных `rowGap` и `columnGap` нет.

`frame` применяется отдельно к каждой ячейке:

| Значение | Толщина |
| -------- | ------: |
| `none`   |    0 px |
| `thin`   |    1 px |
| `medium` |    3 px |
| `thick`  |    5 px |

`frameColor` выбирает один из двух общих сайт-токенов:

```css
--color-image-border
--color-image-border-alt
```

Рамка входит в геометрический расчёт ячейки и justified-строки, чтобы высоты оставались ровными.

## Focal point и обрезка

Управляемое изображение может иметь общую точку фокуса в каталоге:

```ts
type FocalPoint = { x: number; y: number }
```

Обе координаты задаются в процентах `0..100`; дробные значения допустимы. Отсутствующее значение
означает центр `{ x: 50, y: 50 }`. `rect` и `square` передают координаты в `object-position`, чтобы
при кропе сохранялась важная область изображения.

Объект в явном `images` может локально переопределить `focalPoint`. Для `albumId` и `imageSetId`
используется только значение каталога. `justified` не обрезает изображение, поэтому focal point там
не влияет на визуальный результат.

Точка фокуса является редакционным метаданным управляемого изображения, а не свойством
сгенерированного файла. Для канонической фотографии она хранится непосредственно в записи
`src/content/photos/<imageId>.yaml`:

```yaml
focalPoint:
    x: 42.5
    y: 30
```

Поле необязательное, поэтому существующие записи не требуют массового изменения. Generated image
manifest остаётся источником файлов и деривативов и не становится редактируемым хранилищем focal
point. Build resolver объединяет manifest с редакционными метаданными и передаёт результат в
presentation-модель. Для будущих управляемых иллюстраций, портретов и других не-фотографических
изображений эквивалентное поле должно находиться в их канонической записи общего каталога.

## Alt и captions

Разрешение текста совпадает с `Wrap Around` и общими правилами каталога:

- отсутствующий `alt` использует локализованное значение каталога и существующий resolver;
- `alt=""` осознанно помечает изображение декоративным;
- отсутствующий `caption` использует каталог и его fallback-правила;
- строка `caption` заменяет каталог для текущего вхождения;
- `caption={false}` запрещает подпись и inline, и в lightbox.

Overrides доступны только объектам явного `images`. Альбомы и image sets используют общие
метаданные фотографий.

При `inlineCaption=true` подпись располагается overlay внутри ячейки, а не добавляет высоту под
изображением. Так она не разрушает ровную полосу. Пустая разрешённая подпись не создаёт overlay.
`lightboxCaption=true` передаёт то же разрешённое значение в PhotoSwipe.

Декоративное интерактивное изображение всё равно должно дать ссылке доступное имя из метаданных;
пустой `alt` не должен создавать безымянную кнопку или ссылку.

## Действия и lightbox

`ImageAction` общий для `Wrap Around` и `Gallery`:

- `none` — изображение не интерактивно;
- `lightbox` — открыть управляемый оригинал/самый широкий дериватив поверхности `photoswipeSlide`;
- `photo` — перейти на каноническую страницу изображения;
- `album` — перейти в управляемый альбом по `albumId`;
- `custom` — перейти по безопасному внутреннему или разрешённому внешнему адресу.

Итоговое действие явного элемента: `image.action ?? gallery.action ?? 'lightbox'`. Для album/image
set используется общее действие блока. В lightbox-группу входят только элементы с итоговым
`lightbox`; остальные пропускаются без разрыва порядка группы.

`lightboxScope='page'` по умолчанию объединяет совместимые lightbox-элементы страницы, включая другие
блоки. Явный `lightboxScope='block'` создаёт отдельную группу. Анимация определяется по безопасному
правилу группы:

- `rect` и `square` всегда используют `fade`, поскольку zoom из кропа в естественные пропорции
  создаёт скачок;
- `justified` наследует стандартную open animation сайта.

PhotoSwipe использует одну open-анимацию на всю page-группу. Поэтому смешанная группа с хотя бы одним
`rect` или `square` также принудительно использует `fade` для всех своих слайдов: это исключает zoom
из cropped thumbnail. В группе только из `justified` сохраняется настройка сайта. Публичного prop,
который позволил бы включить zoom для crop-layout, нет.

Loop, переходы между слайдами, их длительность и стандартная open animation принадлежат site config.
Параметров `loop`, `openZoom` и `animateTransitions` в MDX нет.

При `action='none'` блок не показывает hover/focus-сигналы интерактивности. Остальные состояния
унифицированы на уровне сайта; отдельных `hoverOpacity`, `hoverBorders`, grayscale и blur нет.

## Lazy loading и клиентский рендер

Lazy loading — обязательное внутреннее поведение всех layout:

- responsive-производные разрешаются общим image pipeline;
- браузер получает intrinsic dimensions/aspect ratio до загрузки пикселей;
- фактические файлы не запрашиваются до приближения выбранного элемента к области видимости;
- элементы, скрытые правилом `mobileFirstOnly`, не загружаются;
- используется нейтральный геометрический placeholder без пользовательского loader;
- после загрузки изображение плавно проявляется через сайт-токены;
- при `prefers-reduced-motion` проявление происходит без анимации.

Публичных `loading`, `lazyjs`, `loader`, `loaderHTML` и `delay` нет. Эти параметры не должны
возвращаться даже ради точного воспроизведения старого шорткода.

Согласованный механизм client random:

1. Astro на сборке разрешает весь допустимый пул через серверный image catalog.
2. Готовая разметка кандидатов помещается в инертный `<template>` внутри блока.
3. Ресурсы из `<template>` не запрашиваются, пока выбранные элементы не перенесены в живой DOM.
4. Страничный координатор выбирает IDs и активирует только итоговый состав.
5. Нативная lazy loading/общий observer откладывают загрузку пикселей до видимости.

Так полный server-only manifest не уезжает в браузер, клиент не дублирует построение URL, а галерея
не делает отдельный JSON-запрос. Цена решения — HTML-разметка всех кандидатов. Для очень больших
пулов её позже можно заменить отдельной статической публичной проекцией без изменения MDX API.

## Progressive enhancement и `<noscript>`

Обычная галерея без `randomCount` рендерит полезный статический HTML и не зависит от JavaScript, за
исключением улучшенного lightbox.

Динамическая галерея требует JavaScript для случайной выборки, поэтому получает `<noscript>`:

- используются первые `randomCount` элементов канонически раскрытого, отфильтрованного и
  отсортированного пула;
- изображения используют нативную lazy loading;
- обычные действия остаются ссылками;
- lightbox-ссылка без PhotoSwipe ведёт к изображению;
- fallback не пытается имитировать random.

HTML должен содержать размеры, семантический контейнер галереи и отдельный `figure` для каждого
активного элемента. Конкретная внешняя обёртка выбирается так, чтобы не создавать невалидное
вложение в Markdown/MDX. Клавиатурный порядок совпадает с визуальным порядком после выборки и
сортировки.

## Ошибки и диагностика

Следующие ситуации блокируют сборку или проверку контента:

- не задан ни один источник;
- неизвестный `imageSetId`, `albumId`, `imageId` или `exclude`;
- пустой явный `images` как единственный источник;
- пустой image set после раскрытия;
- неопубликованное или запрещённое для встраивания изображение;
- повтор внутри одного явного списка, `exclude`, `albumIds`, `photoIds` или `priorityPhotoIds`;
- неизвестное значение enum;
- `columns` вне `1..5`;
- `randomCount` не является положительным целым или превышает постоянный пул после фильтров;
- координата focal point не является конечным числом `0..100`;
- небезопасная custom-ссылка или неизвестная цель `photo`/`album`.

Повторы, появившиеся при раскрытии разных источников image set, не являются ошибкой: они удаляются с
сохранением первого вхождения. Одновременно переданные валидные источники дают диагностическое
предупреждение о проигнорированных параметрах, но не меняют строгий приоритет.

## Рекомендуемая структура реализации

1. Zod-схема валидирует MDX props, image sets, enums, диапазоны и управляемые ссылки.
2. Pure source resolver выбирает источник, раскрывает альбомы, удаляет повторы и применяет
   постоянные исключения.
3. Pure ordering resolver реализует `order` и `priorityPhotoIds`.
4. Build-time media resolver получает каталог и создаёт минимальные presentation-модели кандидатов.
5. Страничный client coordinator делает random в DOM-порядке и учитывает межгалерейные исключения.
6. Astro-компонент рендерит активную/static разметку, `<template>` кандидатов и `<noscript>`.
7. CSS/container queries реализуют три layout, gaps, рамки, focal point и адаптивную плотность.
8. Общий responsive image-компонент отвечает за источники, размеры, placeholder и lazy loading.
9. Существующий PhotoSwipe v5 adapter регистрирует только итоговые lightbox-элементы.

Random, source resolution и layout geometry должны быть независимыми pure-модулями. Компонент не
должен переносить jQuery, Waypoints, PHP-кэш или генерацию responsive URL из legacy.

## Проверки реализации

Минимальный набор автоматических проверок:

- схема покрывает defaults, все enum, строковый shorthand и объектные overrides;
- приоритет источников детерминирован, неизвестный верхний источник не даёт fallback;
- image set раскрывает несколько альбомов и прямые IDs в согласованном порядке;
- межисточниковые повторы удаляются по первому вхождению;
- все шесть `order` и `priorityPhotoIds` покрыты ties и отсутствующим `capturedAt`;
- приоритет не меняет вероятность random и действует только после выборки;
- явный `exclude` применяется до layout-фильтра и random;
- динамический `rect` использует границу `4:3`, а явный rect-список не фильтруется;
- random возвращает ровно `randomCount` уникальных элементов и допускает новый состав при reload;
- межгалерейное исключение работает в DOM-порядке и корректно ослабляется при нехватке кандидатов;
- RU/EN не получают общего seed или persisted-состояния;
- `mobileFirstOnly` не загружает скрытые элементы и не меняет состав при resize;
- rect/square имеют ровные crop-ячейки, justified — ровные строки и `nojustify` в последней;
- focal point берётся из каталога, переопределяется явным элементом и игнорируется в justified;
- рамка входит в геометрию, а `frameColor` не влияет при `frame='none'`;
- inline caption не изменяет высоту ячейки;
- действия наследуются, overrides работают, lightbox-группа фильтрует остальные действия;
- crop использует `fade`, natural preview — сайт-default;
- до активации/видимости кандидаты не создают сетевых запросов изображений;
- `<noscript>` использует первые канонические элементы и остаётся читаемым;
- intrinsic dimensions предотвращают CLS;
- keyboard navigation, focus, accessible names и reduced motion проверены;
- MDX fixture проходит загрузку и статический рендер в обеих локалях.

## Готовность контракта

Публичные редакторские параметры, источники, defaults, порядок преобразований и внутренняя
геометрическая автоматика согласованы. При реализации остаётся проверить формулу justified и
container-переходы на реальном корпусе визуальными fixtures; это проверка принятого контракта, а не
открытая продуктовая развилка.
