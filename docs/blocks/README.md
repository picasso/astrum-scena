# Контентные блоки

Живая спецификация компонентов для сложного контента внутри статей и страниц. Раздел пополняется по
мере разбора WordPress-страниц и их актуальных Gutenberg-блоков. Его задача — дать разработчику
полный контракт каждого блока: редакторские параметры, автоматику, правила рендера, адаптивное
поведение, валидацию и связь с исходной реализацией.

- **Статус:** рабочая спецификация
- **Обновлено:** 2026-09-22
- **Область:** переиспользуемое Astro-ядро для трёх мигрируемых сайтов
- **Приоритет источников:** согласованные решения в спецификации блока → актуальный Gutenberg-блок
  темы `zu` → визуальный пример на старом сайте
- **Вне области:** восстановление legacy-шорткодов и их исторических вариантов

## Реестр блоков

| Блок                            | Назначение                                             | Статус контракта |
| ------------------------------- | ------------------------------------------------------ | ---------------- |
| [`Wrap Around`](wrap-around.md) | Одно или несколько изображений с обтеканием текстом    | согласован       |
| [`Gallery`](gallery.md)         | Адаптивная статическая или динамическая галерея        | согласован       |
| [`Callout`](callout.md)         | Текстовый фрагмент с акцентным оформлением             | согласован       |
| [`Note`](note.md)               | Errata-примечание «что изменилось с момента написания» | согласован       |
| [`Links`](links.md)             | Набор ссылок в конце материала                         | согласован       |

Следующие блоки добавляются в этот реестр после разбора примера, актуального Gutenberg-приёмника и
редакторских требований. Полный контракт каждого блока хранится в отдельном файле этой папки.

Автоматические поверхности, которые detail-страница добавляет после тела документа, не являются
MDX-блоками. В частности, навигация по другим или вручную связанным материалам описана отдельно в
[`MoreDocuments`](../more-documents.md).

## Общие правила

### Формат контента

Обычный Markdown остаётся форматом для простого текста. Текстовые блоки, которые добавляют к
Markdown-фрагменту только оформление и метаданные, записываются контейнерными директивами. Например,
`Callout` использует `:::callout … :::` и может жить в обычном `.md`-файле. На этапе сборки плагин
директивы валидирует её и превращает в статический семантический HTML.

Сложные блоки с медиа и структурированными данными вставляются в MDX как типизированные
Astro-компоненты. В контенте в обоих случаях хранятся только редакторские параметры; готовый HTML,
низкоуровневые responsive-поля изображения и произвольные CSS-классы в документ не попадают.

Загрузка обоих расширений уже реализована (SX1). Коллекции `articles` и `pages` читаются
[`localizedDocumentLoader`](../../src/lib/content/localized-glob.ts): он принимает `.md` и `.mdx`, а
[`localizedDocumentId`](../../src/lib/content/localized-id.ts) даёт одинаковый ID независимо от
расширения. Один документ не может существовать в обоих форматах сразу: Astro на такой дубликат
только предупреждает и перетирает запись, поэтому загрузчик падает сам.

Отсюда редакторское правило импортёра: документ с компонентами сохраняется как `.mdx`, обычный
остаётся `.md`. Компоненты блоков приходят в MDX из общего реестра
[`MDX_COMPONENTS`](../../src/components/content/mdx-components.ts) — в самом документе импортов нет.

Контейнерные директивы включены фичей дефолтного markdown-процессора Astro
(`satteri({ features: { directive: true } })` в [`astro.config.mjs`](../../astro.config.mjs)) и не
требуют смены расширения документа на `.mdx`.

### Управляемые изображения

Все блоки принимают только стабильные идентификаторы изображений из управляемого каталога. Внешние
URL запрещены: сборка не должна зависеть от доступности или неизменности чужого файла.

Используется нейтральное имя `imageId`, а не `photoId`: в тексте могут встречаться не только
авторские фотографии, но и портреты, иллюстрации или другие управляемые изображения.

По `imageId` пайплайн получает URL дериватива, intrinsic width/height, `srcset`, `sizes` и остальные
технические данные. Эти значения не авторятся в MDX. Общее разрешение `alt` и `caption` должно
сохранять семантику [ADR-0009](../adr/0009-alt-caption-derivation.md) и
[модели текстовых полей фото](../design/photo-text-model.md).

### Общая шкала расстояний

Контентные блоки используют один семантический тип расстояния:

```ts
type ContentGap = 'none' | 'tiny' | 'small' | 'medium' | 'large'
```

Для текущего сайта токены имеют следующие значения:

| Токен    | Значение |
| -------- | -------: |
| `none`   |     0 px |
| `tiny`   |     4 px |
| `small`  |     8 px |
| `medium` |    12 px |
| `large`  |    16 px |

Семантические имена остаются частью MDX-контракта, а числа принадлежат дизайн-токенам сайта. Это
позволяет следующему сайту откалибровать ту же шкалу без числовых значений внутри контента.

Реализация: тип и список семантических имён —
[`content-gap.ts`](../../src/lib/blocks/content-gap.ts), единственный источник значений —
CSS-переменные `--content-gap-*` в `src/theme/theme.css`. Блоки берут расстояния из темы, а Gallery
читает вычисленный интервал сетки для расчёта геометрии.

Значения токенов должны быть CSS-длинами (`<length>`): `px`, `rem`, `em` или `calc()` только с длинами,
например `calc(1rem + 2px)`. Нулевой интервал записывается как `0px`, а не безразмерный `0`, чтобы
вычисления Gallery в CSS сохраняли размерность. Проценты, в том числе внутри `calc()`, не
поддерживаются: `getComputedStyle()` не разрешает их в пиксели, необходимые геометрии Gallery.

### Общие модули блоков

| Модуль                                                      | Назначение                                                        |
| ----------------------------------------------------------- | ----------------------------------------------------------------- |
| [`managed-image.ts`](../../src/lib/blocks/managed-image.ts) | `imageId` → модель `<picture>` плюс разрешённые `alt` и `caption` |
| [`safe-link.ts`](../../src/lib/blocks/safe-link.ts)         | Проверка `custom.href` и безопасные атрибуты якоря                |
| [`block-gallery.ts`](../../src/ui/block-gallery.ts)         | Область группировки lightbox: `scope='block'` и `scope='page'`    |

Группировка lightbox опирается на существующий PhotoSwipe-остров. Контейнер блока помечается
`data-block-gallery`, а его якоря используют тот же контракт `a.album-photo` + `data-pswp-*`, что и
альбомная сетка. Страничная группа задаётся общим `data-block-gallery-group` с детерминированным
идентификатором от рендера страницы: адаптер берёт общего предка таких контейнеров как gallery-root
и собирает их снимки в один список слайдов.

### Lifecycle PhotoSwipe

[`PhotoSwipeLoader`](../../src/components/portfolio/photoswipe-loader.astro) подключает общий
[`photoswipe-bootstrap.ts`](../../src/ui/photoswipe-bootstrap.ts) только на совместимых маршрутах.
При импорте bootstrap сразу вызывает идемпотентный `mount()` для уже существующего DOM, затем
повторяет mount на `astro:page-load` для переходов Astro и выполняет teardown на
`astro:before-swap`.

Немедленный первоначальный mount — часть общего контракта, а не особенность Wrap Around. Нельзя
заменять его одной подпиской на `astro:page-load` или полагаться на положение loader в дереве Astro:
момент выполнения вложенного модульного скрипта не должен определять, заработает ли lightbox.
Контентные блоки не создают собственные PhotoSwipe-инстансы: они отдают `data-block-gallery` и
`a.album-photo`, после чего общий bootstrap находит и монтирует все совместимые поверхности.
