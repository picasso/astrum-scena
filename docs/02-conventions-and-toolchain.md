# Конвенции и тулчейн

Адаптировано с проектов владельца (durer-ai, neuro-hub) под статичный Astro-сайт.
Цель — единый стиль и процесс на всех трёх фотосайтах.

## Язык (правило)

- **Русский** — вся содержательная документация в `docs/`: что и зачем делаем, планы, ADR (проза), заметки.
- **Английский** — код, идентификаторы, комментарии в коде, коммиты, `CHANGELOG.md`, PR-заголовки
  и описания, всё git-связанное, agent-ops файл (`AGENTS.md`).

> Отличие от neuro-hub: там PR-описания были русскими. Здесь вся git-история целиком английская.

## Стек

- **TypeScript** strict, path-alias `@/* → src/*`.
- **Astro** (движок, см. ADR-0001) + React-острова для интерактива (PhotoSwipe, hero-слайдер).
- **Tailwind v4**, семантические токены (`bg-background`, `text-foreground`), без сырых hex.
  Тёмная/светлая темы. Дизайн-система обёрнута в `src/ui/` (как в проектах владельца).
    - **Токены живут в CSS, не в JS-конфиге.** В v4 палитра/шрифты задаются директивой `@theme`
      в файле темы `src/theme/theme.css` (его импортирует `src/styles/global.css`) — это единственный
      источник истины. Из `@theme`-переменных Tailwind генерит утилиты (`bg-accent`) и одновременно
      даёт CSS-переменные (`var(--color-accent)`). Цвета в правилах компонентов — только через токены
      темы; цветовой литерал вне файла темы валит `pnpm check:color-literals`.
    - Подключение в Astro: плагин `@tailwindcss/vite` в `astro.config.mjs` + импорт `global.css`
      в базовом layout. Работает и в `.astro`, и в React-островах.
- **PhotoSwipe v5** — viewer. **Swiper.js** — hero-слайдер.
- **sharp** — водяной знак + обработка изображений на сборке.

## Тулчейн

- **Prettier:** табы (ширина 4), без `;`, одинарные кавычки, printWidth 100, trailing commas all.
    - В `.mdx` используются четыре пробела вместо таба: JSX-разметка остаётся визуально согласованной
      с кодом, но не конфликтует с `markdownlint` `MD010/no-hard-tabs`.
    - Плагин `prettier-plugin-tailwindcss-canonical-classes` (сортировка + автозамена
      устаревших имён классов v4, напр. `shadow-sm`→`shadow-xs`) — подключён на S1
      (`global.css` создан, `tailwindcssCanonicalStylesheet` указывает на него).
- **ESLint 10** flat config (`defineConfig` из `eslint/config`): `no-explicit-any: error`,
  `prefer-const: error`, `simple-import-sort`, политика **zero-warning** в CI.
- **Тесты:** Vitest (юнит, co-located `*.test.ts`). E2E — по необходимости (Playwright).
    - **Тесты не привязываются к значениям `site.yaml`.** Конфиг для того и сделан, чтобы владелец
      менял его как угодно; любая валидная правка обязана оставлять тесты зелёными. Проверять
      конкретное значение — значит собрать его в самом тесте (fixture/override) и проверить его,
      а не читать из реального конфига. От боевого конфига допустимы только контрактные проверки:
      что он проходит схему и что набор ключей соответствует ожиданиям кода (у каждой поверхности
      есть запись). Единственное исключение — значение, зафиксированное ADR: такой тест называется
      по ADR и меняется только вместе с ним (пример: `conforms to ADR-0008` в `site.test.ts`).
- **Git-хуки:** Husky + lint-staged (`eslint --fix` + `prettier --write` на staged).
- **Package manager:** pnpm (как в durer-ai). Node 24 (`.nvmrc`, `engines`).
- **CI (GitHub Actions):** typecheck → lint (zero-warning) → format:check → lint:md → test → build.
    - **Lighthouse CI** (performance budget) — **release-blocking с S11 §7**: job в `deploy.needs`,
      `continue-on-error` снят, `numberOfRuns: 3`. Гейтятся perf-score + CLS + TBT + a11y (LCP/FCP —
      advisory, см. обоснование). Baseline, headroom и variance-runbook —
      в документах миграции S11 (репо сайта).

## Процесс работы (правило взаимодействия)

Кодифицировано с проектов владельца:

- **План → подтверждение → реализация → спросить перед коммитом.** Не коммитить без явного запроса.
- **Не запускать сборку** (`build`) без явного указания в агентской сессии.
- **Не подавлять** lint/type-check ради удобства — переписать код.
- **Не добавлять** AI-атрибуцию / `Co-authored-by` без явной просьбы.
- Когда что-то не работает — не «чинить молча», а описать проблему и предложить 2–3 варианта с плюсами/минусами.

## Коммиты

- **Conventional Commits**, английский, императив: `<type>(<scope>): <summary>`.
- Доменные скоупы: `db`, `ui`, `config`, `core`, `docs`, `content`, `images`, `i18n`, `scripts`.
- Тело (при полном сообщении): why/эффект, затем что изменено.
- `CHANGELOG.md` в стиле Keep-a-Changelog.

## Именование и организация

- Файлы — kebab-case; компоненты — PascalCase, именованные экспорты.
- Обработчики — `on*`; булевы — `isLoading`/`hasError`.
- Тонкие страницы: логика в компонентах/утилитах, не в маршрутах.
- Барьеры импорта через `src/ui/` (без прямых импортов сырого shadcn вне `src/ui/`).
