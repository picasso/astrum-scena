# ADR-0004: Раздельный деплой — сайт через CI, картинки в R2

- **Статус:** accepted
- **Дата:** 2026-07-18

## Контекст

Нужны два независимых процесса деплоя:

- **код/контент** — по push в `main` должен деплоиться автоматически из GitHub, без участия локальной машины;
- **фотографии** — отдельная процедура, запускается локально при изменении альбомов.

Cloudflare Pages деплоит атомарный снимок всей папки `dist/`: новый деплой целиком заменяет
набор файлов. Поэтому два независимых деплоя в _один_ Pages-проект невозможны — они затирают
друг друга (деплой кода без картинок убирает картинки, и наоборот). Независимость требует
**разных origin'ов**. Это переопределяет прежнее «R2 откладываем» (ADR-0002): требование
раздельного деплоя как раз и есть обоснование для R2.

## Решение

Два независимых трека деплоя с разными originّ ами и разделением полномочий:

| Трек        | Что                                                              | Откуда           | Куда                             |
| ----------- | ---------------------------------------------------------------- | ---------------- | -------------------------------- |
| 1. Сайт     | код + тексты + метаданные + `src/generated/images-manifest.json` | GitHub push → CI | Cloudflare Pages (`example.com`) |
| 2. Картинки | веб-деривативы                                                   | локальная машина | R2-бакет (`media.example.com`)   |

**Хранилища и роли:**

- **pCloud** — мастера/оригиналы (холодный архив, источник для регенерации, не раздаётся).
- **git/GitHub** — код + двуязычные тексты + метаданные + `src/generated/images-manifest.json`.
- **R2** — веб-деривативы (то, что раздаётся). Бесплатный тариф 10 ГБ, отдача в Cloudflare бесплатна.
- **Cloudflare Pages** — HTML/CSS/JS сайта.

**Мостик — `src/generated/images-manifest.json`:** пайплайн `sharp` выдаёт (а) деривативы → R2 и (б) `src/generated/images-manifest.json`
(размеры, ширина/высота, пути) → git. CI знает про картинки, не держа файлов.

**Имена деривативов — с контент-хешем** (`name-<hash>.avif`): точная проверка наличия,
безопасный деплой (старые версии не перезаписываются), иммутабельное кэширование.

**Разделение полномочий:**

- CI держит токен деплоя Pages + **read-only** R2 → деплоит только сайт, картинки проверяет, но не пишет.
- Локальная машина держит **write** R2 → заливает только картинки, код задеплоить не может.

**Гейт ссылочной целостности** (в обоих треках, единый модуль в `scripts/lib/`):

1. Деплой кода (CI): `check:images-live` — каждая картинка из `src/generated/images-manifest.json` есть в R2, иначе деплой падает.
2. Деплой картинок (локально): `check:derivatives` — манифест ↔ локальные файлы совпадают.
3. Опц.: `images:prune` — отчёт об орфанах в R2.

Гейт превращает порядок «сначала картинки, потом push» из привычки в enforced-правило.

**Механизм деплоя сайта:** **Wrangler с самого старта** (`cloudflare/wrangler-action@v3` в CI,
`command: pages deploy`), Pages-проект типа Direct Upload, конфиг в `wrangler.toml`
(`name`, `pages_build_output_dir`). Нативную Git-интеграцию Cloudflare **не используем** —
она урезает контроль над гейтами и это лишний промежуточный шаг.

**Видимость деплоя в GitHub:** Wrangler заливает через CLI и не создаёт объектов GitHub
Deployments, поэтому панель Deployments/Environments в репозитории остаётся пустой. Чтобы
вернуть видимость, **не меняя механизм**, CI сам регистрирует деплой через GitHub Deployments API
(`actions/github-script` на `GITHUB_TOKEN`, `permissions: deployments: write` у job'а `deploy`):
статус `in_progress` до заливки, `success`/`failure` и `environment_url` — после (URL извлекается
из вывода Wrangler; при неудаче извлечения статус ставится без URL). Это **не** нативная
Git-интеграция Cloudflare: сборка и деплой остаются в CI под контролем гейтов, регистрация деплоя
чисто информационная. Per-PR preview-деплои сюда не входят — регистрируется только production.

## Альтернативы

- **Один Pages-проект, два пайплайна** — невозможно (атомарный снимок затирает).
- **Второй Pages-проект под картинки** вместо R2 — работает, тот же `wrangler`, но неидиоматично
  и каждый деплой пересобирает полный снимок картинок. R2 честнее (инкрементальный синк).
- **Картинки в git (LFS)** — отвергнуто: тяжёлый git, и деплой перестаёт быть раздельным.
- **Сборка картинок в CI из бакета** — отвергнуто: противоречит «фото деплоим локально».

## Последствия

- (+) Код деплоится сам из GitHub; картинки — отдельно и локально. Ровно как требовалось.
- (+) Битый сайт со ссылками на несуществующие картинки невозможен (гейт целостности).
- (+) git лёгкий; безопасные деплои и иммутабельное кэширование за счёт контент-хешей.
- (−) Четыре места хранения (pCloud/git/R2/Pages), но у каждого чёткая роль.
- (−) CI получает read-only доступ к R2 (приемлемо — только проверка, не запись).
- (+) Панель GitHub Deployments отражает production-деплои, при этом контроль над деплоем
  остаётся в CI (Wrangler) — видимость добавлена без перехода на нативную Git-интеграцию.
- Порядок при добавлении альбома: сначала деплой картинок в R2, потом push кода.

## Обновление (S10 Block A) — единый release-дескриптор

Мостик перестал быть двумя tracked-файлами. Прежде active-состояние жило в
`src/generated/images-manifest.json` (embedded manifest) **и** `config/images-live-policy.yaml`
(phase/active/allowlist). S10 Block A объединяет их в один tracked source of truth —
`src/generated/images-release.json` (схема — `src/lib/images/release.ts`). Дескриптор содержит phase,
`active`, allowlist, config digest, версию схемы манифеста и **embedded** canonical-манифест; все
readers active-состояния (`check:images-policy`, `check:images-live`, live-e2e, activation) читают
только его. Формат хранения сменился — семантика и байты манифеста нет: `serializeManifest` embedded-
манифеста байт-идентичен прежнему `images-manifest.json`. Оба старых tracked-файла удалены. Активация
теперь переключает **один** файл одним атомарным `rename` под journaled-recovery (вместо двухфазной
замены manifest+policy).

## Обновление (S11) — клиентские build-time переменные в CI-сборке

Следствие CI-сборки, которое легко упустить: **сайт собирается в GitHub Actions**, а не нативной
Git-интеграцией Cloudflare. Поэтому переменные окружения из **дашборда Cloudflare Pages биндят только
рантайм Function** (`context.env`) — до `pnpm build` в CI они **не доходят**. Любая клиентская
build-time переменная (`PUBLIC_*`, которую Astro вшивает в бандл через `import.meta.env`) должна
задаваться как **GitHub Actions repository variable** и явно прокидываться в шаг Build (`env:` в
`ci.yml`). Пример: `PUBLIC_TURNSTILE_SITE_KEY` контактной формы (ADR-0002 §S11 §5) — заданная только в
дашборде, она оставляет клиентский бандл без site key, и Turnstile не выдаёт токен. Секреты формы
(`TURNSTILE_SECRET_KEY`, `TELEGRAM_*`) этого не требуют: их читает Function в рантайме из дашборда.

## Обновление (S14/01a) — единая лестница и manifest v3

Действующий tracked source of truth — `src/generated/images-release.json`: он содержит `active`,
`configDigest` и embedded manifest v3. У фото один массив деривативов; ключ каждого файла имеет вид
`<photoId>/<width>w-<sha256>.<format>`, без сегмента роли. CI проверяет каждый объект активного
дескриптора в R2 до деплоя сайта. Локальный цикл: `images:build` → `check:derivatives` →
`images:sync --real` → `check:images-live` → `images:activate`. Активация по-прежнему атомарно
переключает один tracked-файл с journaled recovery. Старые ключи в R2 не удаляются и не
перезаписываются. Правило ширин, знака и прямого перехода зафиксировано в [ADR-0014](0014-image-width-ladder.md).
