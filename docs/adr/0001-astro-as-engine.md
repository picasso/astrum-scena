# ADR-0001: Astro как движок сайта

- **Статус:** accepted
- **Дата:** 2026-07-18

## Контекст

Персональный фотосайт мигрирует с WordPress. Сайт по сути статичный: показ альбомов,
фотографий, viewer, эссе. Обновляется редко, ценность — долговечность и минимум обслуживания.
Владелец фокусно работает на Next.js 16 + React 19 (проекты durer-ai, neuro-hub), и рассматривался
вариант делать сайт на привычном Next ради однородности.

## Решение

Движок — **Astro** (статическая генерация). Поверх Astro адаптируется весь тулчейн и процесс
владельца (см. `docs/02-conventions-and-toolchain.md`).

## Альтернативы

- **Next.js 16 (static export)** — максимальная однородность с другими проектами владельца,
  можно форкнуть конфиг и UI-кит. Отвергнуто как основной движок: тяжёлая машинерия Next
  (Effector, Kysely, Better Auth, RSC-данные) в его проектах нужна для _приложений_, а фотосайт —
  это _контент_, эти части не используются. Плюс `next/image` в static export слабее по
  image-оптимизации, чем `astro:assets`, а для фотосайта обработка картинок — ключевая функция.
- **Специализированные генераторы галерей** (thumbsup, sigal) — минимум работы, но нет контроля
  над дизайном и не переиспользуют тулчейн владельца.
- **Заморозка WP в статику** — отвергнуто: владелец хочет заодно переработать организацию альбомов.

## Последствия

- (+) Лучший инструмент под статичный фото-контент: `astro:assets`, ноль JS по умолчанию, острова.
- (+) Переиспользуется самое ценное из стека владельца — тулчейн и процесс (переносятся на Astro),
  а также React-компоненты (shadcn-обёртки) через острова.
- (+) Долговечный HTML на выходе, минимум обслуживания.
- (−) Сам фреймворк Astro владельцу нов (митигируется агентской разработкой — руками пишется мало).
- (−) Часть Next-специфичных навыков не переиспользуется — но они для фотосайта и не нужны.
