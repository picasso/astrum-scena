# ADR-0014: Единая лестница ширин изображений

- **Статус:** accepted
- **Дата:** 2026-09-26
- **Связано:** ADR-0004, ADR-0008, S14/01a

## Контекст

Прежний пайплайн выпускал отдельные наборы файлов для ролей `thumbnail`, `grid`, `viewer` и `hero`.
Одинаковые ширины повторялись в R2, а поверхность выбирала роль вместе с её профилем водяного знака.
Для 17 опубликованных фото это давало 292 файла и 20 810 984 байт. Решение владельца после P06:
знак защищает скачанный файл; его видимость после экранного кропа не является требованием.

## Решение

Секция `images` файла `site.yaml` задаёт одну лестницу `200, 400, 800, 1200, 1600` и нативную ширину
мастера. Файл выпускается только если не превышает мастер по ширине и 2000 px по длинной стороне.
Нативный верх равен `min(sourceWidth, floor(2000 × sourceWidth / max(sourceWidth, sourceHeight)))`.
Нечётные ширины небольших мастеров сохраняются; апскейла нет. Каждая пара `(width, format)` встречается
в фото один раз. Для каждой ширины выпускаются AVIF и WebP: при `width ≤ 800` качество 50/72, выше
порога — 55/78.

Знак определяется **шириной файла**, одинаково для горизонтальных и вертикальных фото. Файлы до
800 px включительно выпускаются без знака; файлы шире получают единый профиль `watermark` из ассета
`dr-watermark`: масштаб 0,17, диапазон 96–384 px, правый нижний угол, отступ 24 px, непрозрачность
0,8. Если мастер не даёт файла шире 800 px, сборка предупреждает, а `images:ladder-report` перечисляет
фото. Исключений из правила нет.

Манифест версии 3 хранит плоский массив `derivatives[]` у фото. Каждый файл содержит собственный
`watermarkProfile`, а ключ имеет вид `<photoId>/<width>w-<sha256>.<format>`. Поверхность выбирает из
этого массива файлы в пределах своего потолка: 400 px для миниатюр футера, 800 px для превью и всю
лестницу для баннера, основной фотографии и PhotoSwipe. HTML `sizes` остаётся ответственностью
компонента. В одном `srcset` теперь могут стоять чистые и маркированные файлы: это сознательное
следствие защиты скачанного файла.

Переход прямой: runtime и tooling читают только config v2 / manifest v3. Сначала полный релиз
собирается и проверяется локально, затем загружается в R2 и активируется одним переключением
tracked-дескриптора. Старые R2-объекты остаются нетронутыми. Для локального просмотра служит
`pnpm dev:local-images [--release <id>]`; `images:ladder-report --pixels` повторно проверяет пиксели.

## Альтернативы

- Сохранить роли и дедуплицировать только файлы с одинаковыми байтами: роль продолжала бы управлять
  знаком и оставляла бы неоднозначный контракт `srcset`.
- Поднимать знак в «безопасную зону» баннера или делать отдельные широкие кропы: владелец отклонил
  после локального просмотра. Баннеры сохраняют текущую композицию.
- Читать оба формата манифеста в runtime: добавило бы постоянные ветки и усложнило проверку
  публикации. Переключение кода и релиза проводится вместе.
- Оптимизировать каждый небольшой мастер отдельно: ради 17 фото это усложняло бы воспроизводимость
  без значимого выигрыша. Ширина мастера остаётся верхней ступенью.

## Последствия

Для текущего корпуса релиз `s14-width-ladder-01` содержит 194 файла и 14 300 049 байт: на 98 файлов
и 6 510 935 байт меньше прежнего `s12-full-corpus`. Пиксельная проверка всех 194 файлов дала ноль
расхождений. `san-marco-moon` (мастер шириной 711 px) не имеет маркированного файла до замены мастера;
замена входит в отдельную задачу.

Preview-поверхности получают только чистые файлы. Полноэкранный просмотр может получать файл со
знаком. Для широких баннеров и PhotoSwipe 2× на всех экранах недостижимо из-за предела 2000 px по
длинной стороне; это явное исключение в ADR-0008. При добавлении фотографии нужно собрать и проверить
новый релиз, загрузить его в R2 и только затем активировать tracked-дескриптор.
