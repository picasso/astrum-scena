# Стримлайн исходного сайта и общее ядро для тонких сайтов

## Why

**Боль и замысел.** Исходный сайт рос заплатками. В итоге:

- миграционный код и тесты крутятся в проверках живого сайта;
- одни и те же данные грузятся и пишутся несколькими путями;
- гейты дублируются, а CI пропускает часть из них;
- `global.css` разросся до 4274 строк;
- идентичность сайта зашита в код.

Это мешает работе уже сейчас. Замысел: один растущий код ядра, на котором три бывших WordPress-сайта
владельца (№1, №2, №3) живут как тонкие репозитории. Сайт только
кастомизирует ядро и получает новые возможности обновлением версии, как когда-то тема zu получала
ZUKIT. Сайт №1 закончен, поэтому отложенный ADR-0003 вопрос о форме общего ядра пора закрыть.

## Capabilities

Номера фаз и пунктов `EH-*` — из `STREAMLINE-CATALOG.md`, решения `AD-*` — из `ARCHITECTURE-SPINE.md`.

- **CAP-1**
  - **intent:** Проверки живого сайта исполняют только код рабочего режима; миграционный код, данные и
    тесты изолированы и не достижимы из рантайма (фаза B1, AD-11).
  - **success:** `pnpm check` и `pnpm test` не запускают ни одного миграционного теста или CLI;
    граф импортов от маршрутов и живых скриптов не достигает миграционной зоны; `/factcheck` работает
    на `src/content`; ESLint запрещает импорт `src → scripts` и миграционной зоны из рантайма
    (EH-21…EH-29, EH-15, EH-32, EH-35 — часть).
- **CAP-2**
  - **intent:** В репозитории нет мёртвого кода и ложных утверждений в доках и комментариях, а CI
    обеспечивает каждый гейт ровно один раз (фаза A, AD-14).
  - **success:** EH-01…EH-14, EH-16…EH-19, EH-30, EH-31, EH-33, EH-34, EH-57…EH-59, EH-61, EH-62
    закрыты; job CI `gates` содержит все гейты `pnpm check`; ни один тест не дублирует drift-гейт;
    стилевые правила и подавления проверяет ESLint. Перед переносом 6.2 выполнен единый пакет 5.13
    по `SPEC-pre-core-fixes`; его CAP-ID локальны этому пакету.
- **CAP-3**
  - **intent:** У каждого источника данных один загрузчик и одна схема, у каждого производного
    артефакта — одна команда-писатель (фаза B2, AD-9, AD-10).
  - **success:** EH-36…EH-40, EH-49 закрыты; grep не находит чтения `site.yaml` или дескриптора изображений в
    обход загрузчика; ни один SKILL.md не предписывает ручную правку производного поля.
- **CAP-4**
  - **intent:** Повторно используемые вычисления получают данные и конфиг явно, адаптеры загружают
    источники сайта; идентичность и локали живут в конфиге, теме и контенте (AD-6, AD-8, AD-22, AD-24).
  - **success:** EH-41…EH-45, EH-20 закрыты; гейт идентичности не находит домена, имени владельца или
    литерала локали в коде; маршруты строятся из одного набора, параметризованного локалью; ESLint
    запрещает скрытую зависимость вычислительных модулей от конфига и допускает необходимые загрузки
    явно определённых IO/Astro-адаптеров. Чистота всего `lib` не является критерием готовности.
- **CAP-5**
  - **intent:** Стили принадлежат компонентам, живут в слоях каскада, а CSS варианта приходит только
    для варианта, выбранного в конфиге (фаза B4, AD-25).
  - **success:** EH-46, EH-50…EH-56 закрыты; общий файл стилей содержит только Tailwind, шрифты, токены, базу и
    прозу; гейт цветовых литералов зелёный; замер покрытия показывает меньший объём CSS на страницу, чем
    до B4.
- **CAP-6**
  - **intent:** Ядро выпускается версионируемым пакетом из собственного публичного репозитория с
    демо-сайтом, без единого следа исходного сайта и окружения владельца (фаза C; AD-1, AD-2, AD-7,
    AD-16, AD-22).
  - **success:** репо ядра публичен после зелёного гейта идентичности; демо-сайт собирается из
    упакованного артефакта ядра; снапшот-гейты публичного API зелёные; релиз помечен semver-тегом;
    ADR перенесены по карте AD-16 (правила — в ядро, значения — в умолчания).
- **CAP-7**
  - **intent:** Тонкий сайт кастомизирует ядро только через публичный API (переопределения конфига с
    lock-файлом, тема, контент, словари, ограниченные точки визуальной замены, черновики `site-*`) и
    обновляется сменой версии с видимым diff эффективного конфига (AD-3, AD-4, AD-19, AD-20, AD-23,
    AD-24).
  - **success:** у сайта нет импортов внутренних путей ядра; `site.lock.yaml` совпадает с результатом
    `core config resolve`; обновление ядра, изменившее умолчание, проявляется diff'ом lock-файла, а не
    молчаливой сменой вывода. Визуальные замены сохраняют интерактивную оболочку ядра; широкая полная
    замена компонентов добавляется при конкретной потребности сайта.
- **CAP-8**
  - **intent:** Различия сайтов выражаются опциональными модулями ядра, которые объявляют манифест и
    включаются конфигом (AD-5, AD-18).
  - **success:** курсы переведены в модуль с манифестом; сборка падает на коллизии маршрута, коллекции,
    MDX-имени или i18n-ключа между ядром, модулями, черновиками и контентом.
- **CAP-9**
  - **intent:** Миграция WordPress-сайта выполняется набором migrate-wp, не знающим конкретного сайта,
    и ставится в сайт только на фазу миграции (AD-11).
  - **success:** migrate-wp — отдельный пакет; особенности источника — адаптеры (qtranslate, одноязычный
    WP, WP Media Folder, zu-media, форматы записей); соответствия — конфиг миграции сайта; флаг
    `migration.closed` удаляет его из сайта.
- **CAP-10**
  - **intent:** Операции сайта (изображения, валидация, гейты, миграция, конфиг), content-ops skills,
    пресеты тулчейна и CI поставляются ядром одной версией, а инфраструктура и окружение остаются у
    каждого сайта своими (AD-12, AD-13, AD-14, AD-15, AD-20).
  - **success:** в `package.json` сайта — только алиасы на CLI ядра; skills и workflow несут штамп
    версии ядра, и гейт падает при расхождении; CI сайта — переиспользуемый workflow ядра; ядро знает
    только имена переменных окружения и корней `*_ROOT`, не их значения.
- **CAP-11**
  - **intent:** Сайт №1 работает как тонкий репо на выпущенной версии ядра (AD-17).
  - **success:** новый репо сайта №1 собирается из закреплённой версии ядра и проходит полный CI;
    визуальные эталоны и e2e совпадают с последним выпуском исходного сайта; деплой идёт из нового репо.

- **CAP-12**
  - **intent:** У ядра есть минимальная документация: что это, как сайт его подключает, что можно
    кастомизировать (публичный API) и как обновляться.
  - **success:** по документации, без чтения кода ядра, можно поднять демо-сайт и настроить его; каждый
    элемент публичного API (AD-7) в ней описан; версионированный `UPGRADING.md` позволяет пройти
    цепочку ломающих выпусков от установленной версии до целевой по примерам, порядку действий и
    проверкам. Универсальная команда миграции не требуется; отдельные скрипты добавляются по пользе.
- **CAP-13**
  - **intent:** Любое добавление в ядро идёт по описанной процедуре — от идеи или черновика на сайте до
    модуля или изменения ядра — с обязательными проверками (опирается на AD-4, AD-7, AD-18).
  - **success:** процедура описана в репо ядра; изменение ядра не принимается без её проверок (манифест,
    снапшоты публичного API, версия, CHANGELOG, документация); перенос сайта №1 проходит по ней.

## Constraints

- Решения `ARCHITECTURE-SPINE.md` (AD-1…AD-25) обязательны; противоречащая им реализация — конфликт,
  который поднимается, а не локальное исключение.
- Порядок фаз жёсткий: A → B1 → B2 → B3 → B4 выполняются в исходном репо под действующими гейтами, и
  только затем C (вынос). Зависимости пунктов — в каталоге.
- Архитектурное разделение вводится по пользе для качества сайта, переноса, проверки и сопровождения;
  массовая переработка ради соответствия начальным формулировкам не является целью.
- Спайк 6.1 проверяет реальный выбор CSS пакета с альбомом внешнего потребителя; 6.2 разводит
  package/site roots, собирает автономное демо без dev/E2E-флагов и объединяет чтение мест.
- Первая кастомизация ограничена темой, настройками и небольшим набором визуальных точек; поведение
  интерактивных компонентов поддерживает ядро.
- Совместимость оценивается семантически по AD-7; стабильность байтов требуется для значимых
  хешей/адресов/повторного использования артефактов.
- `src/content` — единственный редактируемый источник контента (ADR-0012); стримлайн не переписывает
  контент.
- Стек: Astro static + TypeScript 6 (пин ADR-0005), Tailwind v4, Cloudflare (хостинг + R2) на каждый
  сайт; бесплатные лимиты (R2 ~10 ГБ, вероятно на аккаунт; минуты Actions для приватных репо) — бюджет
  на все сайты.
- Репо ядра становится публичным только после зелёного гейта идентичности.
- Истина о старых сайтах — только локальные деревья по именованным корням `*_ROOT` из `.env`; удалённые
  копии ею не являются.
- Тесты не закрепляют значения конфига реального сайта (AD-21).

## Non-goals

- Портирование сайтов №2 и №3: следующие инициативы, их порядок задан AD-17, требования —
  в `sites-inventory.md` (репо сайта).
- CMS или визуальное управление сайтом для владельца.
- Периодичность обновления и решение о «заморозке» отдельных сайтов.
- Выбор Pages или Workers для новых сайтов.
- Редизайн сайта №1 или новые пользовательские функции.

## Success signal

- Новый тонкий репо сайта №1 с закреплённой версией публичного ядра деплоит сайт, совпадающий с
  нынешним по визуальным эталонам и e2e. В репо ядра нет ни одного следа исходного сайта, а
  демо-сайт, собранный только из упакованного ядра, показывает, что второй сайт можно начать без
  копирования кода.

## Assumptions

- Стримлайн сохраняет опубликованный вывод сайта №1 (визуальные эталоны и e2e остаются
  зелёными), кроме сознательного удаления мёртвого CSS и кода: владелец просил упростить, а не
  переделать.
