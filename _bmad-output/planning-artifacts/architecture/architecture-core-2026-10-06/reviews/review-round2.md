## 2. New problems introduced by the revision

### N1 (high) AD-14 lets CI write to R2, contradicting ADR-0004 and AD-15

AD-14 says "запись в R2 и деплой — только на push в `main`". ADR-0004 (kept by AD-15 and AD-16) says
CI holds only a **read-only** R2 token and writes derivatives only from the local machine (the seed
diagram agrees). Read literally, the reusable workflow may receive an R2 write secret.

**Fix:** AD-14 should read: "CI holds the deploy token and read-only R2; deploy only on push to `main`;
R2 is written only locally (ADR-0004)".

### N2 (high) AD-19 "image digest from lock" contradicts AD-7 "no shape change requires an image re-run"

`core upgrade` renames or reshapes an images-config key (AD-7 compliant). Re-resolving changes the
lock bytes, which changes `configDigest` (today's `canonicalStringify` after parse). The descriptor's
digest then mismatches, `check:images-policy` goes red, and recovery needs masters plus R2. On top of
that, any *additive* defaulted image field is now forced to be a major.

**Fix:** compute the digest over a core-defined, versioned projection of the derivative-affecting
image fields (`digestVersion`). `core upgrade` must keep that projection stable, or the change is
declared a major with a documented re-run.

### N3 (high) The lock covers only `site.yaml`, but today's config is five files

Today the config is spread across `site.yaml`, `seo.yaml`, `config/images.yaml`,
`place-gps-bounds.yaml` and the domain enums. AD-19 says nothing about the others. A core can obey
AD-7 by giving `images.yaml` its own schemaVersion and defaults, resolved at runtime. That is exactly
the silent default change AD-19 exists to stop, and it makes "digest from lock" ambiguous. The seed
tree silently drops `config/`.

**Fix:** AD-19 should read: "every core-read config file (site, seo, images, gps bounds, domain enums)
is one `site.yaml` override tree resolved into the single `site.lock.yaml`; taxonomy and featured are
content, not config".

### N4 (high) AD-10's single writer conflicts with AD-7's `core upgrade`

AD-7 says `core upgrade` rewrites site files offline, which includes the descriptor/manifest, the
ledgers and the master registry. AD-10 names `core images activate` and `core factcheck` as the *only*
writers of those files. Two writers per artifact again.

**Fix:** in AD-10, `core upgrade` delegates to each writer's `--upgrade` mode and never writes the
bytes itself (or AD-10 lists schema migration as an explicit exception).

### N5 (medium) The migrate-wp lifecycle conflicts with AD-11 "phase"

AD-20 requires a migrate-wp version-match gate, and AD-13 installs `import-wp` through the skills
installer. Together they keep migrate-wp a permanent dependency of every living site. Adversary H10
(no `migration: closed` state) is still open.

**Fix:** migrate-wp and `import-wp` are installed only during the migration phase. The AD-20 check
applies only when migrate-wp is present, and the kit refuses to write after a `migration.closed`
flag in the lock.

### N6 (medium) AD-22 cannot be satisfied as worded

- migrate-wp tests (`data/legacy/fixtures`), `e2e/fixtures/image-site`, the visual baselines and the
  ADR-0011 self-domain list all carry origin-site content and live in the core repo (AD-2).
- The identity gate's denylist (domains, bucket and account IDs) cannot itself be committed to a
  public repo.

**Fix:** core fixtures, demo and baselines must be synthetic, and real corpora stay in the site's
`migration/`. The gate should be pattern-based, with any concrete denylist coming from a CI secret or
the local `.env`.

### N7 (medium) The "every core-read file carries schemaVersion" convention is ambiguous for content

Read literally, it means a frontmatter field in hundreds of MD/MDX/YAML entries.

**Fix:** use one version per collection/data set (in the lock or the manifest), not per entry.

### N8 (low) AD-21 key-set contract has no clear target under a sparse `site.yaml`

The key-set check must target the lock. Once it does, it duplicates the strict lock schema plus the
drift gate (AD-14 one-gate rule).

**Fix:** drop it or redefine it as "lock passes the strict schema".

### N9 (low) Dev loop vs AD-20

The envelope's `pnpm link` dev loop makes the AD-20 stamp/version gate red locally.

**Fix:** allow a declared link mode, or run the gate only in CI.

### N10 (low) Draft config section is not validated against anything

The strict lock (AD-19) must validate draft `site.<id>` sections. AD-18 should state that resolve
validates them against the draft manifest's schema.

### N11 (nit) Hosting wording leans to Pages

`functions/` in AD-15 and the seed is Pages-specific, while hosting is deferred. Say "platform
wrapper (Pages `functions/` or Worker entry)".

## 3. Adversary re-run: two compliant units that still diverge

- **Core v1.5 ↔ pinned site (N2).** Core v1.5 ships an AD-7-compliant images-config rename with
  `core upgrade`. The site runs upgrade and then resolve (exactly the envelope's sequence), and the
  image policy goes red. This is the narrowed remnant of H2. It is high, not critical: it is gated,
  not silent, but the cost is a media rebuild on an archival site.
- **Core reading `images.yaml` defaults at runtime ↔ site relying on the lock diff (N3).** A changed
  images default ships silently. This is the exact hole AD-19 was written to close.
- **Reusable workflow given an R2 write secret ↔ ADR-0004 local-only writes (N1).** This is a trust
  boundary break, not a divergence in output.

No remaining **critical** hole: the namespace, version-skew, i18n, override and draft classes are
closed. Apply N1–N4 (one-line edits each) and the spine is READY-WITH-NITS.
