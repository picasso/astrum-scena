## Проверка требований против действующего кода

### F1 — сериализация и актуальность deploy

- `.github/workflows/ci.yml:15` действительно разделяет main runs по SHA. Публикация в `:501–507` выполняет `pages deploy --branch=main` без проверки актуального HEAD. Указание в spec, что это установленная возможность гонки, а не наблюдавшийся инцидент, точно отражает силу доказательства.
- Сериализация только публикации сохраняет параллельность проверок. Freshness check внутри общей секции закрывает старый rerun и поздно дошедший A; запрет публикации при ошибке проверки достаточен для fail-closed поведения.
- Требование не оставлять ложный GitHub deployment существенно: существующие Start/Finish steps находятся в `ci.yml:483–499,509+`. Их действительно нужно связать с тем же разрешением публикации. Spec это явно требует.
- Проверка реальных workflow bindings в `scripts/ci-config.test.ts` уже применяется для final gates; добавить защиту для новых deploy steps в тот же suite реально. Отдельный общий framework не нужен.
- Один только `git fetch`/checkout текущей ветки не доказывает безопасность: тест должен сохранять привязку артефакта к `github.sha`, как требует spec. Не обнаружено требования собирать или деплоить непроверенное новое содержимое main.

### F2 — входной бюджет и Telegram

- Реальная схема применяет общий лимит 4096 к сумме UTF-8-байт `name/email/message`; `buildTelegramText` добавляет 41 ASCII-символ для EN/RU locale. Пример из spec соответствует ранее проведённому эксперименту реальных функций: accepted=true, input4096, Telegram4137.
- Консервативный общий byte limit с резервом обеспечивает требуемое свойство и для кириллицы/emoji; поиск максимально возможного ввода или обрезка текста не нужны. Правило остаётся общим для клиента и сервера.
- UI сейчас отображает для любой ошибки поля message строку `requiredMessage` (`contact-form.tsx:264`), поэтому требование понятной ошибки длины потребует реальной правки обработки ошибок/строк. Это работа внутри указанного scope, а не недостающая зависимость архитектуры. Tests формы перечислены в карте кода.
- Test transport уже поддерживается через `ContactDeps.fetch`, а `handleContact` проводит валидацию до upstream. Проверить ноль siteverify/sendMessage calls без внешней сети возможно. [Официальный Telegram API](https://core.telegram.org/bots/api#sendmessage) ограничивает сформированный текст 4096 символами; новый byte budget резервирует служебный текст сверх этого ограничения, а не меняет контракт API.

### F4 — publication ledger

- `scripts/lib/images/ledger.ts:28–40` действительно лишь парсит JSON и делает type assertion. `recordPublication` сравнивает только ключ из releaseId/manifestDigest; неполная запись такого ключа может подавить добавление полной. Кейс spec корректен.
- `sync.ts:106` делает первый `client.head`, а чтение журнала происходит лишь внутри `recordPublication` в `:144` после загрузок. Требование проверить журнал до первого вызова R2 требует переноса чтения/preflight, а не уже выполнено текущим локальным gate.
- Existing fake client и deps в `sync.test.ts` позволяют доказать zero calls для malformed ledger. Dry-run также делает HEAD-запросы: формулировка «до первого R2-вызова» охватывает его и не допускает случайной проверки только write-path.
- Физический номер строки требует сохранять исходный индекс до удаления пустых строк. Критерий поздней физической строки это покрывает; существующее `.filter(...).map(...)` придётся изменить.
- Текущие atomic rename, ENOENT-only fallback и семантическая идемпотентность могут сохраниться. Spec не требует чинить данные или вводить schemaVersion раньше 6.3.

### F5 — CSS gap и браузерная геометрия

- Описана реальная цепочка: `CONTENT_GAP_PX` → `GalleryViewModel.gapPx` → inline `--gallery-gap`/`data-gallery-gap` → `Number(dataset.galleryGap)` в координаторе. `--content-gap-*` действительно обходится этой цепочкой.
- Перевод CSS на общий токен и чтение фактического CSS gap при `applyJustifiedGeometry` укладывается в существующий ResizeObserver lifecycle. Требование повторного учёта при resize технически исполнимо.
- Default Playwright config намеренно исключает `gallery-*.spec.ts`; отдельный portfolio harness запускает `gallery-harness.spec.ts` в четырёх viewport projects, а visual projects — при `PORTFOLIO_VISUAL=1`. Поэтому spec правильно требует дополнительный Docker Gallery/portfolio run, а не объявляет `pnpm test:e2e:docker` достаточным.
- CI уже запускает portfolio reusable workflow с `PORTFOLIO_VISUAL=1`; contact e2e также имеет отдельный контейнерный маршрут. Указание брать команды из актуального workflow верно и не ссылается на отсутствующий npm script.
- Геометрический браузерный тест нужен: jsdom-тесты координатора не доказывают вычисленные CSS-расстояния. Spec явно требует измерять геометрию и сетки, и justified rows.

- AD-8 больше не обещает чистоту всего `lib` и разводит явные вычисления и адаптеры. Это соответствует разрешённому направлению работы и не требует массового нецелеобразного рефакторинга.

- Semver и последовательные переходы `UPGRADING.md` не вводят новой внешней технологической зависимости. Отказ от универсального migrator и постоянной поддержки N−1 согласован с сохранением writer ownership для производных файлов.
- Новых technology/version pins, требующих связывающей проверки latest на вебе, изменение не вводит. Установленные Node24/Playwright1.61.1 и существующие test orchestration учтены; утверждений «это последняя версия» не сделано.
