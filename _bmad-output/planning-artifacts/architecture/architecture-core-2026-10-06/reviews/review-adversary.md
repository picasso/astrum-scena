# Adversarial review — Architecture Spine «общее ядро и тонкие сайты»

## Вердикт

**Не готов как build-substrate.** Спайн хорошо фиксирует *направление зависимостей* (AD-3, AD-8) и
*единственность писателя* (AD-10), но почти не фиксирует **владение именами и формами данных на шве
ядро↔модуль↔сайт** и **что считается ломающим изменением кроме схемы `site.yaml`**. Поэтому две
единицы, обе послушные букве AD, расходятся в трёх классах мест:

1. **Пространства имён без владельца** — коллекции контента, сегменты маршрутов, ключи i18n, имена
   MDX-компонентов и директив, CSS-токены, имена skills. Их создают ядро, модули и черновики сайта, а
   реестра и проверки коллизий нет.
2. **Upgrade-контракт уже, чем то, что сайт хранит** — AD-7 версионирует только `site.yaml`, а сайт
   трекает ещё манифест/дескриптор изображений, `src/generated/*`, таксономию, реестр мастеров,
   ledger'ы, установленные skills. Плюс «новое поле с дефолтом — неломающее» (AD-7) в этом коде
   *ломает*, потому что `configDigest` и `layout-tokens.css` считаются от конфига с подставленными
   дефолтами.
3. **Четыре независимых пина «одного» ядра** — пакет (lockfile), workflow `@tag` (AD-14),
   скопированные skills (AD-13), migration kit (AD-11). Ни один AD не требует, чтобы они совпадали.

Ниже — пары, каждая с доказательством соблюдения AD, механизмом поломки, опорой в коде и
предлагаемым правилом (одна строка).

## Пары (детально)

### H1 — Модуль без манифеста: коллекции, маршруты, ключи, nav, MDX, директивы

**Пара A: ядро-интеграция ↔ `src/content.config.ts` сайта.**
- Ядро соблюдает AD-3 (сайт импортирует `albumSchema` и т.п. только из `exports`), AD-5 (tours —
  опциональный модуль, включается *конфигом сайта*), AD-9 (одна схема на источник).
- Сайт соблюдает AD-3: его `src/content.config.ts` импортирует только экспортированные схемы и
  загрузчики.
- Поломка: в Astro коллекции объявляет файл *проекта* (сейчас `src/content.config.ts` —
  `export const collections = { albums, articles, pages, photos }`). Включение модуля tours
  флагом в `site.yaml` **не может** добавить коллекцию `tours` — её должен руками добавить сайт. Итог:
  два переключателя одной фичи (`site.yaml: modules.tours` и строка в `content.config.ts`), которые
  могут разойтись в обе стороны: модуль включён — коллекции нет (маршруты ядра падают на
  `getCollection('tours')`); коллекция есть — модуль выключен (данные валидируются, но не
  рендерятся, `content:validate` о них не знает). Спайн нигде не говорит, кто владеет определениями
  коллекций. Если Astro ^7 не даёт интеграции инъекцию коллекций (на сегодня — Starlight-паттерн
  «пользователь пишет `docsLoader()/docsSchema()` в своём файле»), владелец физически — сайт.

**Пара B: ядровой модуль tours ↔ страница контента сайта со slug `tours`.**
- Оба соблюдают все AD: модуль инжектит `/{locale}/tours/`, а generic page `/{locale}/{slug}/`
  (`pageHref` в `src/lib/content/routes.ts`) — уровень 3 лестницы, контент сайта.
- Поломка: коллизия маршрута. Сегодня это лечится частным костылём только для курсов
  (`createSitemapFilter(courseSlugs)` в `astro.config.mjs`), общего реестра зарезервированных
  сегментов нет. Коллизии file-route ↔ injected-route в Astro по умолчанию — предупреждение и выбор по
  приоритету (жёсткий отказ — opt-in; проверить для ^7), т.е. тихий выбор победителя.

**Пара C: два модуля (video ↔ reviews) или модуль ↔ черновик.**
- Каждый добавляет MDX-компонент в реестр без импорта (`MDX_COMPONENTS` в
  `src/components/content/mdx-components.ts` — плоский `Record<string, unknown>`) и/или
  директиву `:::name` (mdast-плагины в `astro.config.mjs`).
- Поломка: `<Player>` или `:::quote` от двух владельцев — последний `{...spread}` молча побеждает;
  содержимое `.mdx` сайта (авторский текст!) меняет рендер при bump ядра без единой ошибки.

**Пара D: nav.** `navItems` в `src/i18n/ui.ts` — константа ядра с жёстким списком сегментов и
спецслучаем `courses`. Модуль tours и черновик сайта оба хотят пункт меню; порядок — чей?

**Rule (новый AD «Манифест модуля»):** модуль (ядровой или черновик) объявляется один раз
манифестом вкладов (коллекции, сегменты маршрутов, секция конфига, namespace i18n, MDX/директивы,
токены, nav); интеграция строит из манифестов всё, и сборка падает на любой коллизии имён между
ядром, модулями, черновиками и slug'ами контента.

### H2 — «Неломающее» изменение по AD-7/AD-16 ломает закреплённый сайт

**Пара: ядро v1.4 ↔ ядро v1.5 на одном сайте №1.**
- v1.5 добавляет в схему `config/images.yaml` новое поле с дефолтом — по AD-7 это **неломающее**
  minor. Или меняет дефолт ширины лестницы/контейнера — по AD-16 это «значение по умолчанию ядра»,
  схема не тронута.
- Поломка 1 (изображения): `computeConfigDigest` (`scripts/lib/images/config.ts:289`) хеширует
  `canonicalStringify(config)` *после* `imageConfigSchema.parse` — т.е. с подставленными
  дефолтами (`.default([])`, `.default({ ignoreDirs: [] })`). Новый дефолт → новый дайджест →
  `check:images-policy` сравнивает `configDigest` трекаемого `images-release.json` с пересчитанным →
  **красный гейт на каждом сайте после bump без единой правки сайта**. Починка — не переписывание
  файла, а прогон пайплайна на машине владельца с мастерами и загрузка в R2 (ADR-0004: изображения
  только локально). Для заархивированного сайта №2 («почти нулевой уход») это значит, что
  обновление ядра блокировано пересборкой всех медиа.
- Поломка 2 (layout): `serializeLayoutTokens` (`src/lib/layout-tokens.ts`) — писатель ядра; если v1.5
  меняет дефолт `layout.prose` или добавляет токен, трекаемый `src/generated/layout-tokens.css`
  расходится → `check:layout-tokens` красный, а визуально сайт меняется, хотя владелец ничего не
  выбирал.
- Ничего не нарушено: AD-7 соблюдён (поле с дефолтом), AD-10 соблюдён (писатель один), AD-14 соблюдён
  (drift-гейт проверяет). Сломано именно сочетание.

**Rule (ужесточение AD-7 + AD-16):** значения по умолчанию материализуются в конфиг сайта командой
`core upgrade`; смена дефолта или выходных байт писателя — ломающее изменение, а дайджесты считаются
от объявленного автором конфига плюс `schemaVersion`, а не от распарсенного с дефолтами.

### H3 — Четыре независимых пина ядра

**Пара A: сайт (lockfile `core@1.4`) ↔ reusable workflow `@v1.6` (AD-14).**
- AD-14: «CI сайта — переиспользуемый workflow из репо ядра, подключённый по тегу». AD-1: «сайт
  закрепляет версию». Ни один AD не требует, чтобы тег = версия пакета.
- Поломка: workflow v1.6 вызывает гейт/флаг, которого нет в CLI v1.4 (или наоборот — гейт v1.6 с
  новой семантикой проверяет данные v1.4). CI красный или, хуже, зелёный по контракту, которого
  нет в рантайме.

**Пара B: core CLI ↔ skill.**
- AD-13: skills «устанавливаются в `.claude/skills` сайта командой ядра» — это *копии* в репо сайта.
  Сайт делает `pnpm up core` и забывает переустановить skills — skill v1.4 вызывает команду,
  удалённую/переименованную в v1.5 (ровно то, что AD-13 должен был предотвратить).
- Вторая трещина той же пары: AD-12 оставляет в `package.json` сайта «тонкие алиасы». Сегодня skills
  вызывают `pnpm <script>` — имена алиасов принадлежат сайту, а skill — ядру. Сайт переименовал
  алиас — skill сломан при полном соблюдении AD-12/AD-13.

**Пара C: migrate-wp ↔ сайт.** AD-11: kit — «отдельный пакет со своими тестами», AD-8: kit
импортирует IO и SCHEMA ядра. Какой версии? Kit, собранный против схем v2, пишет контент, который
`content:validate` сайта на v1 отвергает (или наоборот, пишет поле, которое v1 молча режет `.strict()`
— fail-closed, т.е. импорт падает целиком).

**Rule (новый AD «Одна линия релизов»):** workflow исполняет CLI из lockfile сайта, skills и
migrate-wp штампуются версией ядра при установке, и always-on гейт падает, если workflow-tag, штамп
skills или версия migrate-wp ≠ установленной версии ядра. (Плюс: skills вызывают бинарь CLI ядра
напрямую, а не алиасы `package.json` сайта.)

### H4 — Формы данных вне `site.yaml` без upgrade-контракта

**Пара: ядро v1 (манифест `schemaVersion: z.literal(3)`, `src/lib/images/manifest.ts:46`) ↔ ядро
v2 (манифест v4).**
- AD-7 говорит о «схеме конфига». AD-9 перечисляет источники (конфиг, дескриптор, манифест,
  таксономия, images-конфиг) — «одна схема», но не «версионированная схема». Сайт трекает
  `src/generated/images-release.json` со встроенным манифестом.
- Поломка: литерал версии → после bump сайт не читает свой собственный трекаемый манифест; новый
  можно получить только пайплайном с мастерами + R2. То же для таксономии
  (`src/content/config/*.yaml`), featured, `place-gps-bounds.yaml`, factcheck-ledger, реестра мастеров
  (`data/legacy/master-matches.jsonl`, живой — читается resolver'ом и `add-album`), фронтматтера
  контента (схемы — ядро, данные — сайт).
- Ни один AD не нарушен: схема одна (AD-9), писатель один (AD-10), конфиг не трогали (AD-7).

**Rule (расширение AD-7 на все данные):** каждый файл сайта, который читает ядро, несёт
`schemaVersion`; ядро читает N и N−1 либо `core upgrade` переписывает его офлайн, и никакое
изменение формы не может требовать повторного прогона пайплайна изображений/R2.

### H5 — Владелец ключей i18n

**Пара A: ядро ↔ словарь сайта.** Сегодня `export type UIKey = keyof typeof en`, где `en` —
`src/i18n/en.json`, по AD-3.3 — словарь *сайта*. Ядровые компоненты вызывают
`t('viewer.moreInfo')`.
- Ядро v1.5 добавляет компонент с `t('viewer.download')` (minor, конфиг не тронут → по AD-7 не
  ломающее). У закреплённого сайта в словаре ключа нет: `dict[key] ?? en[key]` → `undefined` в
  разметке. Тип `UIKey` при этом выводится из файла сайта, т.е. ядро типизируется *по данным
  сайта* — направление зависимостей AD-8 перевёрнуто.
- **Сайт №2 ru-only (AD-6)**: фолбэк зашит на `en` (`defaultLang = 'en'`, `?? en[key]`) — у
  сайта нет `en`-словаря вообще.

**Пара B: модуль tours ↔ сайт.** Модуль добавляет `tours.conditions.title`. Кто поставляет
переводы — модуль (тогда это не «словарь сайта», AD-3.3) или сайт (тогда модуль нельзя включить
без правки словаря — второй переключатель, см. H1)? Уже сегодня `moreDocuments.course.heading` =
«More Tours/Другие туры» — словарь сайта несёт доменный смысл ядровой сущности.

**Rule:** ядро и каждый модуль поставляют словари по умолчанию для своего namespace ключей;
словари сайта — частичные переопределения, проверяемые по объединённому набору ключей для каждой
локали из конфига; отсутствующий ключ — ошибка сборки, а не рантайм-фолбэк на литерал локали.

### H6 — Контракт переопределения шире, чем «имя слота и пропсы»

**Пара: ядровой `PhotoGrid` + PhotoSwipe-остров ↔ override сайта (AD-3.4).**
- Ядро гарантирует имя слота и пропсы (буква AD-3). Override сайта принимает те же пропсы.
- Поломка 1: скрипт viewer'а ядра ищет элементы по data-атрибутам/классам (65 классов `zu-*` в
  `global.css`, атрибуты PhotoSwipe). Override, отрисовавший разметку иначе, — viewer молча не
  открывается. Ядро v1.5 переименовывает хук — все override'ы мертвы, пропсы не менялись.
- Поломка 2 (Tailwind v4): классы утилит в компонентах ядра, лежащих в `node_modules`, не
  попадают в автоматическое сканирование Tailwind (оно игнорирует `node_modules`/gitignored пути) —
  нужен `@source` на пакет ядра. Чей это `@source` — ядра или сайта? Не сказано.
- Поломка 3 (тема, AD-3.2): токены `@theme` (`--color-accent`, `--color-menulink`,
  `--text-hero`…) — фактически публичный API, но CSS не падает на неизвестной переменной. Ядро
  переименовывает `--color-alt` → `--color-accent-2` в minor — тема сайта молча игнорируется.

**Rule:** контракт переопределяемого компонента — пропсы + DOM-хуки (data-атрибуты/id, которые
ищут скрипты ядра) + читаемые токены, экспортированные типизированными списками; гейт сайта падает
на неизвестном/отсутствующем имени, переименование любого из них — major.

### H7 — Черновик → модуль: переход ломает данные

**Пара: черновик `src/drafts/tours` сайта №2 (v1.x) ↔ модуль ядра tours (v1.y после
продвижения).**
- Черновик соблюдает AD-4: только публичный API, своя коллекция `tours` в `content.config.ts` сайта,
  свои данные `src/content/tours/*.yaml`, свои ключи, свой маршрут `/ru/tours/`.
- Сопровождающий продвигает фичу (AD-4), естественно перепроектируя схему для второго сайта.
- Поломка: в момент bump и черновик, и модуль владеют `tours` (коллекция, сегмент, ключи) — см. H1;
  после удаления черновика данные сайта в форме черновика не проходят схему модуля. AD-4 говорит
  «сайт удаляет черновик», но не «что происходит с контентом черновика». Второй сайт, писавший свой
  черновик той же фичи, получает два несовместимых входа.
- Конфиг черновика положить некуда: `site.yaml` `.strict()` и принадлежит ядру (AD-7), значит
  черновик держит свой конфиг-файл, который после продвижения должен уехать в `site.yaml` в иной
  форме — без команды миграции.

**Rule:** черновик живёт в зарезервированном namespace сайта (`site-*` для коллекции, сегмента,
ключей, skill), а релиз продвижения поставляет codemod, переносящий данные черновика в форму
модуля.

### H8 — Три владельца локалей и origin

**Пара: `astro.config.mjs` сайта ↔ `site.yaml` сайта (+ ядро).** Сегодня:
- локали — `i18n.locales: ['en','ru']`, `defaultLocale: 'en'` в `astro.config.mjs`;
- опорная — `content.referenceLocale: ru` в `site.yaml` (а схема — `z.enum(['en','ru'])`,
  `src/config/site.ts:494`);
- `defaultLang = 'en'` в `src/i18n/ui.ts`; `localeSchema = z.enum(['en','ru'])` в схемах.
- origin — `SITE_ORIGIN` в `routes.ts` → `astro.config` `site`; ещё раз в `config/images.yaml`
  (`publicOrigin`, `rights.webStatement: https://example.com/rights/`, `rights.source`), и
  `RIGHTS_PATH` в ядре, на который ссылаются **уже опубликованные байты** изображений (XMP).

AD-6 говорит «локали — конфиг сайта», AD-15 — «ядро не знает доменов», но `astro.config.mjs` — тоже
файл сайта, и Astro i18n остаётся там. Сайт №3 задаёт `locales: [en, ru, de]` в `site.yaml` и
забывает `astro.config` — оба файла «конфиг сайта», AD соблюдены, маршруты и хрефы расходятся.
Смена origin или `RIGHTS_PATH` ядром — тихо невалидирует webStatement в опубликованных картинках.

**Rule:** интеграция — единственный владелец `site`, `i18n` и производных значений Astro (из
`site.yaml`), `astro.config` сайта их не задаёт (интеграция падает, если задал), а значения,
вшиваемые в опубликованные байты (webStatement, rights path), выводятся из того же поля.

### H9 — Одна сущность, два владельца; межмодульные ссылки

**Пара: ядро (`pageSchema.kind: z.literal('course')`, `courseStatus`, маршруты `/courses/`) ↔
модуль tours (AD-5).** «Курсы» сайта №1 — это фототуры (в словаре прямо «More Tours / Другие
туры» для `moreDocuments.course`). Сайт №2 включает модуль tours. Теперь «тур» в ядре — это и
`page` с `kind: course`, и сущность модуля. AD-5 перечисляет «курсы» как модуль, но в коде это
поле базовой схемы ядра.

**Пара: модуль reviews ↔ модуль tours.** Отзыв ссылается на тур (`tourId`). Сайт включает reviews
без tours — ссылки висят; `content:validate` (cross-collection integrity) не знает о модульных
коллекциях. Спайн не описывает зависимости между модулями.

**Rule:** у каждой доменной сущности ровно один владеющий модуль; модули объявляют зависимости, и
включение модуля без его зависимостей — ошибка валидации конфига.

### H10 — Migration kit как второй писатель живого контента

**Пара: migrate-wp (`import-wp`) ↔ живой сайт после фазы миграции.**
- AD-11: «миграция — фаза»; AD-13: `import-wp` в списке ядровых skills, ставится в *каждый* сайт;
  AD-10: `src/content` исключён из правила одного писателя.
- Поломка: после ручных правок владельца (ADR-0012, рабочий режим) запуск kit'а (full overwrite или
  «additive re-bootstrap») снова пишет `src/content`. Все AD соблюдены, «фаза» — это лишь намерение,
  не состояние. Владелец сайта №3 (Deferred: CMS), получает в агенте skill, который может
  перезаписать её контент.

**Rule:** kit пишет только в staging-дерево, перенос в `src/content` идёт через
`content:validate`, а после записанного в конфиге `migration: closed` команды kit отказываются
писать.

### H11 — Demo-сайт ≠ реальный сайт

**Пара: `demo/` в репо ядра ↔ сайт №1.** Demo в монорепо ядра резолвит ядро через workspace —
видит исходники, файлы вне `files`/`exports`, devDependencies ядра. Реальный сайт ставит пакет
(git-зависимость или registry, Deferred). AD-3 запрещает глубокие импорты, но demo физически может их
делать и «Deferred: содержимое демо — покрыть публичный API» не требует покрыть **оси конфига**: demo
на `en+ru`/опорная `ru` никогда не проверит ru-only сайт №2 (AD-6) или опорную `en`.

**Rule:** демо потребляет ядро только из упакованного tarball (`pnpm pack`, exports в силе) и
прогоняется по матрице осей конфига: 1 локаль, не-`ru` опорная, каждый модуль вкл/выкл.

### H12 — Одна CSS-переменная, два источника

**Пара: config-проекция ↔ тема сайта.** `--container-prose|medium|standard|gallery` пишет
`layout:tokens` из `site.yaml` (уровень 1) в `src/generated/layout-tokens.css`. Тема (уровень 2,
`src/theme/`) — «CSS-токены» без перечня. Сайт кладёт `--container-prose: 720px` в тему: каскад
решает порядок подключения, гейт `check:layout-tokens` зелёный (файл совпадает с конфигом), а
реальная ширина — из темы. Аналогично `--color-*` могли бы прийти из `site.yaml` (accent для
баннеров `bannerAccentSchema`).

**Rule:** у каждой CSS custom property ровно один источник: токены, проецируемые из конфига,
зарезервированы, и гейт темы отвергает их объявление в `src/theme`.

### H13 — Файлы, которые платформа требует в корне сайта

**Пара: ядро (`src/lib/contact/handle.ts`) ↔ `functions/api/contact.ts` сайта.** Cloudflare Pages
берёт функции только из `functions/` проекта; Astro-интеграция не может их инжектить. Сегодня файл
импортирует `../../src/lib/contact/*` — после выноса это либо копия кода ядра (нарушение AD-1), либо
реэкспорт из неэкспортированного пути (нарушение AD-3), либо «ручной» файл без писателя (AD-10). То
же для `public/_redirects`, `robots.txt` (утечка идентичности из сканов), `wrangler.toml`.

**Rule:** файлы, которые платформа требует в корне сайта (`functions/*`, `public/_redirects`,
`robots.txt`), генерирует CLI ядра как производные артефакты (AD-10) в одну строку-реэкспорт, с
drift-гейтом.

## Мелочи (не дыры, но шум на шве)

- `src/pages/e2e-harness/[view].astro` — тестовый маршрут в дереве страниц; при выносе — только в
  demo, иначе интеграция инжектит его каждому сайту (его `getStaticPaths` пуст вне e2e, но маршрут
  занимает namespace — см. H1).
- AD-13 «свои skills сайта не могут занимать имя ядрового skill» не покрывает обратный порядок:
  ядро v1.5 добавляет `add-tour`, а у сайта №2 уже есть свой `add-tour`. Покрывается H7
  (`site-*` namespace) + инсталлятор, отказывающийся перезаписывать неучтённые файлы.
- Общий архив мастеров (`IMAGES_MASTERS_ROOT`) для двух сайтов одного фотографа: реестр мастеров —
  в каждом сайте, кэш — в `.cache/` репо; конфликта записи нет, но один мастер получит два
  независимых `photoId`. Не дыра, но стоит явной строки в спайне, чтобы никто не «оптимизировал» в
  общий реестр.
- Смена `referenceLocale` в `site.yaml` (уровень 1) требует переписать Tier-1 поля в контенте
  (уровень 3, ADR-0013) — нужна команда миграции наравне с AD-7.
