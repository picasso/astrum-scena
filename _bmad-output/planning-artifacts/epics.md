# Astrum Scena — Epic Breakdown

Требования — из SPEC (вместо PRD), архитектурные правила — из spine, конкретная работа — из каталога
стримлайна. ID `CAP-*`, `AD-*`, `EH-*` — из этих документов, не перенумеровываются.

## Requirements Inventory

### Capabilities (SPEC)

- CAP-1: проверки живого сайта исполняют только код рабочего режима; миграция изолирована.
- CAP-2: нет мёртвого кода и ложных доков; CI выполняет каждый гейт ровно один раз.
- CAP-3: один загрузчик и схема на источник данных, один писатель на производный артефакт.
- CAP-4: логика получает конфиг на вход; идентичность сайта и локали — только в конфиге, теме,
  контенте.
- CAP-5: CSS у компонентов, в слоях каскада, варианты — только выбранные.
- CAP-6: ядро — версионируемый пакет в публичном репо с демо-сайтом, без следов исходного сайта.
- CAP-7: тонкий сайт кастомизирует ядро только через публичный API, обновляется сменой версии с
  видимым diff lock-файла.
- CAP-8: опциональные модули с манифестом и гейтом коллизий; курсы — эталонный модуль.
- CAP-9: migrate-wp не знает конкретного сайта и ставится только на фазу миграции.
- CAP-10: CLI, skills, пресеты и CI поставляются ядром одной версией; инфраструктура — у сайта.
- CAP-11: Сайт №1 работает как тонкий репо на выпущенной версии ядра.
- CAP-12: у ядра есть минимальная документация: подключение, публичный API, обновление.
- CAP-13: любое добавление в ядро идёт по описанной процедуре с обязательными проверками.

### Constraints (SPEC)

- решения AD-1…AD-25 обязательны.
- порядок фаз A → B1 → B2 → B3 → B4 → C; A–B4 в исходном репо под действующими гейтами.
- опубликованный вывод сайта не меняется — визуальные эталоны и e2e зелёные, кроме сознательного
  удаления мёртвого.
- `src/content` не переписывается (ADR-0012).
- стек — Astro static, TypeScript 6, Tailwind v4, Cloudflare на сайт; бесплатные лимиты общие.
- ядро публично только после зелёного гейта идентичности.
- тесты не закрепляют значения конфига реального сайта.

### Additional Requirements

- Архитектурные правила — `ARCHITECTURE-SPINE.md`, AD-1…AD-25.
- Работа по пунктам — `STREAMLINE-CATALOG.md`, EH-01…EH-62 с фазами и зависимостями.
- До фазы C — однодневный спайк канала поставки пакета ядра (открытый вопрос SPEC).

### UX Design Requirements

Нет: редизайн вне скоупа (Constraints).

### Story 6.1: Package delivery spike

_Спайк канала поставки пакета_

Objective:

- Delivery context: вынос ядра (истории 6.2–6.9) и каждый будущий тонкий сайт.
- Primary outcome: выбран и проверен на практике способ, которым сайт ставит и обновляет ядро.
- Why it matters: от канала зависит устройство репо ядра, релиза и CI сайта; ошибка выяснится только
  после выноса.

**Acceptance Criteria:**

- [x] На учебном пакете в отдельном репо сравнены три канала — git-теги с `#semver:`, GitHub Packages,
      публичный npm: установка и обновление, пакет из подкаталога репо (`core` и `migrate-wp` рядом),
      выпуск двух пакетов (общая версия по AD-20 — решение владельца в 6.1), peer-зависимости (`astro`, `react`), запуск `bin` из собранного
      JS, работа в CI без личного токена.
- [x] Проверено на текущей версии pnpm проекта.
- [x] На учебном пакете и текущей версии Astro интеграция из пакета отдаёт маршрут с
      `getStaticPaths`, коллекцию контента, MDX-компонент, виртуальный модуль и CSS, классы которого
      видит Tailwind через `@source`; что не работает — ограничение в ADR спайка.
- [x] Проверена реальная цепочка `variantCssPlugin`: CSS установленного пакета и альбом внешнего
      сайта читаются из разных корней. Tarball установлен в отдельную папку вне source workspace;
      сборка работает без копии `src/components` и при cwd, отличном от Astro root. Найденные
      зависимости от размещения файлов записаны для исправления в 6.2 (AD-8).
- [x] Выбор записан ADR'ом и закрывает открытый вопрос SPEC о канале поставки.
- [x] Учебный репо удалён или помечен как архив.

### Story 6.1b: Tailwind source boundary

_Граница источников классов Tailwind_

Objective:

- Delivery context: CSS сайта до переноса в 6.2 ([BK17](../../docs/backlog/bk17-tailwind-source-boundary.md)).
- Primary outcome: правка документа, спека, скрипта или текста статьи не меняет CSS сайта.
- Why it matters: Tailwind сканировал весь репо, и класс из документа менял бандл и ронял
  `check:page-budget` (5.10, PR #65).

**Acceptance Criteria:**

- [x] `src/styles/global.css` задаёт источники явно: `src/` без `src/content`; документы, спеки,
      скрипты и тексты статей на CSS не влияют.
- [x] Исчезнувшие правила перечислены в `docs/design/css-baseline.md`, ни одно не используется в `src/`.
- [x] `content:validate` отклоняет атрибут `class` в `src/content` с файлом и строкой; оформление статей
      — только через компоненты и директивы.
- [x] Регрессии в `pnpm check` или CI падают, если границу снять: класс-метка из документа не попадает
      в CSS, класс компонента `src/` попадает, `global.css` держит границу.
- [x] `pnpm check`, `pnpm build`, `check:production-build`, `check:page-budget` и
      `pnpm test:e2e:docker` проходят без перезаписи эталонов; бюджет ужат с записью причины.
- [x] CSS пакета ядра и демо (`@source` пакета) не входит — это 6.2.

### Story 6.2: Core repo and demo site

_Репо ядра и демо-сайт, ставящий ядро из упакованного артефакта_

Objective:

- Delivery context: вынос ядра и будущие тонкие сайты.
- Primary outcome: есть отдельный репо ядра с Astro-интеграцией из кода, прошедшего эпики 1–5, и
  демо-сайт, который ставит ядро так же, как настоящий сайт.
- Why it matters: демо из исходников не доказывает, что ядро работает как пакет.

**Части истории (решение владельца 2026-10-26):** 6.2 выполняется частями, каждая — своя запись в
`sprint-status.yaml`; критерии ниже закрываются частями так:

- **A** — каркас репо и гейт утечек
  ([spec](../implementation-artifacts/spec-6-2a-core-skeleton-and-leak-gate.md)): pnpm-workspace со
  структурой AD-2, интеграция-заглушка с одним маршрутом, демо из `pnpm pack` в CI, гейт утечек,
  `check:local-paths`, хук `commit-msg`, вычищенные `AGENTS.md`, правила, skills и `_bmad`.
- **A2** — перенос кода эпиков 1–5 вместо заглушки и разведение корней (AD-8)
  ([spec](../implementation-artifacts/spec-6-2-a2-port-core-code.md)).
- **A3** — гейты исходного кода ядра в `pnpm check` (ESLint, цветовые литералы, слои CSS,
  комментарии, маршруты, токены раскладки) с путями ядра и корня сайта
  ([spec](../implementation-artifacts/spec-6-2-a3-core-source-gates.md)).
- **A4** — `noUncheckedIndexedAccess` для `packages/core` (`tsconfig.json` и `tsconfig.build.json`),
  закреплённый тестом в `pnpm check` (решение владельца 2026-10-26: вынесено из A3)
  ([spec](../implementation-artifacts/spec-6-2-a4-strict-index.md)).
- **A5** — 17 тестов на реальном контенте, переписанные на фикстуры демо и включённые в
  `pnpm check` (решение владельца 2026-10-27: вынесено из A4, после флага); решение владельца
  2026-10-29: разделена на три части. **A5a** — конфиг и файловые контракты (`config/{loader,privacy,seo}`,
  `lib/content/{rights-route,translation-freshness}`, `theme/fonts`, `components/site-logo`, правила
  `lib/redirects/contract`) ([spec](../implementation-artifacts/spec-6-2-a5a-config-and-file-contracts.md)).
  **A5b** — рендер компонентов на фикстурах (`components/{cards,top-section,blocks/gallery.render,content/privacy-render,status/status-route}`).
  **A5c** — `components/{shell,content-surfaces}`, `lib/featured` (слияние с тестом ядра) и
  `lib/blocks/links/corpus`. Сверка ссылок статей с замороженной выгрузкой и реального `_redirects`
  остаётся в исходном репо референсом паритета 9.3.
- **B** — `CHANGELOG.md` ядра.
- **C** — демо покрывает публичный API, изображения демо; решение владельца 2026-10-27: разделена
  на три части. **C1** — вторая локаль `ru` и текстовый контент демо (страница `privacy`, статья,
  курс, `rights.ru.md`), доступная запасная главная без `featured`, проверка страниц документов в
  сборке из tarball
  ([spec](../implementation-artifacts/spec-6-2-c1-demo-locales-and-text-content.md)). **C2** —
  изображения демо; решение владельца 2026-10-27: разделена на две части. **C2a** — ядро: функция
  нарезки исходника (мастер-буфер → `sharp` → лестница AVIF/WebP с водяным знаком → запись манифеста
  v3), схема и загрузчик `config/images.yaml`, проекция в `images-public.json` и поле `publicPath`,
  взаимоисключающее с `publicOrigin` (`publicOrigin` остаётся только HTTPS); писатель прав
  инъецируемый, без него `rightsEmbedded: false`, права в XMP через ExifTool — 6.7
  ([spec](../implementation-artifacts/spec-6-2-c2a-core-derivatives-and-public-path.md)). **C2b** —
  демо: генератор процедурных изображений на функции нарезки ядра в `public/` демо, альбомы, фото и

  **C3** — долг эпика 5: семантика `mediaSource` и гипотезы о мёртвом коде.
- **D** — e2e и визуальные эталоны с демо. **E** — общая загрузка мест (AD-9).
  **F** — релизный workflow (dry-run). **G** — заморозка исходного репо и правило в `AGENTS.md`.
- Сайтовые skills и агенты в репо ядра не переносятся (удалены в A): версии под CLI ядра — 6.7,
  `import-wp` — эпик 8.

### Story 6.3: Public API snapshot gates

_Публичный API и снапшот-гейты, `schemaVersion` у файлов сайта_

Objective:

- Delivery context: репо ядра и каждый сайт, который его обновляет.
- Primary outcome: публичный API ядра явно объявлен, а его изменение видно в CI до релиза.
- Why it matters: без этого обновление ядра ломает сайты молча (AD-7).

**Acceptance Criteria:**

- [ ] `exports` пакета ядра объявлены явно; демо импортирует только их, глубокий импорт падает на
      lint-правиле ядра (AD-3).
- [ ] Объявлен поддерживаемый API потребителя: `exports`, схемы файлов сайта, имена MDX-компонентов
      и директив, токены, ключи i18n, документированные CLI/env. Снапшот-гейты проверяют его; внутренние
      переменные runners и тестовые протоколы не становятся API сайта (AD-7).
- [ ] Изменение снапшота валит CI, пока снапшот не обновлён в том же PR; удаление или сужение
      помечается как ломающее изменение.
- [ ] Ломающим считается требование изменить конфиг/контент/код сайта или перевыпустить деривативы.
      npm-версия ядра отдельна от репо-версии: репо и CHANGELOG продолжают нумерацию исходного репо
      (`1.<epic>.<story>`, с 1.6.x), а пакет ядра остаётся `0.x` до принятия первым сайтом в 9.3 —
      `0.<epic>.<story>` выпускающей истории (решение 6.9, первая публикация — `0.6.9`): ломающим

      хеши/адреса (`configDigest`, ключ деривативов, `translatedFromDigest`) сохраняют свой байтовый
      контракт под golden-тестом (AD-7).
- [ ] Версионированный `UPGRADING.md` (разделы по npm-версии ядра) описывает каждый ломающий
      переход: версии, изменения с примерами «до/после», порядок, версии нужных писателей и проверку

      пропущенных выпусков; отдельный скрипт добавляется по необходимости. `check:upgrading`
      проверяет структуру, PR-гейт требует запись для каждого ломающего изменения снапшота (AD-7).
- [ ] Каждый файл сайта, который читает ядро, несёт `schemaVersion`: `site.yaml`, `seo.yaml`,
      `images.yaml`, файлы таксономии и наборов изображений, `featured/home.yaml` и сгенерированные
      `images-public.json` и `images-release.json`; `version` в `images.yaml` переходит на него без

- [ ] Файл без `schemaVersion` или с неподдерживаемой версией даёт ошибку с именем файла и списком
      поддерживаемых версий.

### Story 6.6: Module manifest and collision gate

_Модули с манифестом и гейт коллизий; курсы — эталонный модуль_

Objective:

- Delivery context: демо-сайт и сайты, которым нужны курсы или будущие модули.
- Primary outcome: модуль включается одной строкой конфига; всё, что он добавляет, объявлено в его
  манифесте.
- Why it matters: сейчас курсы вшиты в шесть мест и строятся всегда; манифест убирает ручной
  рассинхрон и ловит коллизии имён на сборке (AD-18).

**Acceptance Criteria:**

История делится на две части (решение владельца 2026-11-14): A — манифест, `modules.<id>` и курсы
как эталонный модуль (`spec-6-6a-module-manifest-and-courses-module.md`); B — гейт коллизий имён,
поверхность `modules` в API-снапшоте и негативная сборка демо с намеренной коллизией.

Часть A:

- [ ] Модуль объявляет манифест: коллекции, сегменты маршрутов, секцию `modules.<id>`,
      i18n-пространство, MDX- и директивные имена, токены, пункты меню, зависимости (AD-18);
      зависимость на выключенный или неизвестный модуль — ошибка.
- [ ] Курсы вынесены в модуль с собственной коллекцией `src/content/courses/` (`kind: course` и
      `courseStatus` уходят из страниц): без `modules.courses` нет маршрутов, коллекции, пункта меню
      и записей в sitemap (AD-5); пункт меню сайт пишет сам, сегмент выключенного модуля или
      неизвестный сегмент — ошибка с путём ключа.
- [ ] `src/content.config.ts` сайта — одна строка вызова построителя ядра, который собирает коллекции
      из ядра и включённых модулей (по lock).
- [ ] Секция `modules.<id>` в lock проверяется схемой из манифеста модуля (AD-19); настройки курсов
      переезжают в `modules.courses`, `site.yaml` получает `schemaVersion: 3`.
- [ ] Контент выключенного модуля и цель `moreDocs` на него — ошибка сборки, а не молчаливый пропуск.
- [ ] Модуль поставляет свой словарь в своём пространстве (`courses.*`); полнота ключей проверяется
      по правилам 6.5 (AD-23), словарь сайта переопределяет ключи только включённых модулей.
- [ ] Демо включает модуль курсов с синтетическими курсами; упакованное демо собирается и без модуля.

Часть B:

- [ ] Сборка падает на коллизии имён между ядром, модулями и slug'ами контента — тест на демо с
      намеренной коллизией; поверхность `modules` входит в API-снапшот.

- [ ] Есть матрица форматов и случаев — горизонтальный, вертикальный, квадрат, панорама, широкий для
      hero; цвет и ч/б; каждая ячейка привязана к маршруту или раскладке демо (justified, masonry,
      featured, обложки, галерея статьи).
- [ ] Агент предлагает из портфолио реальные снимки, покрывающие матрицу; владелец утверждает отбор.
- [ ] Агенты пишут промпты по утверждённым снимкам — жанр, композиция, свет, без людей, узнаваемых
      мест, брендов и имени владельца (AD-22); промпты лежат в репо ядра.
- [ ] Связь «промпт → исходный снимок» и сами снимки в репо ядра не попадают.
- [ ] Владелец генерирует фото по промптам в GPT Images вручную; скрипты и CI к API не обращаются.
- [ ] Скрипт нарезает сгенерированные фото по форматам матрицы; параметры кадрирования лежат в репо,
      повторный прогон даёт те же файлы.
- [ ] Разрешения хватает на самый крупный дериватив ядра, иначе это отмечено и максимальный размер в
      демо понижен осознанно.
- [ ] Скрипт пишет синтетические EXIF и GPS в границах мест демо, чтобы пайплайн выводил дату, место и
      `colorMode` как для настоящих фото.
- [ ] Мастера закоммичены, суммарный размер ≤ 50 МБ проверяет гейт; README указывает, что фото
      сгенерированы, и их лицензию CC0.
- [ ] Заглушки удалены, визуальные эталоны пересняты (EH-47).

### Story 6.13: Core-written files and the site's formatter

_Файлы, которые пишет и сверяет ядро, не ломаются форматтером сайта_

Objective:

- Delivery context: каждый сайт на ядре с пресетом Prettier ядра; найдено пробной сборкой 6.8, до 9.1.
- Primary outcome: `prettier --check .` сайта проходит на файлах, которые пишет ядро, а
  `prettier --write .` не ломает их гейты.
- Why it matters: сейчас пресет Prettier ядра переписывает `site.lock.yaml` (кавычки),
  `src/generated/images-public.json` (массивы) и установленные skills и агенты (пустая строка после
  штампа), после чего падают гейты `config-lock`, `images-public-config` и `skills`; репо ядра прячет
  это корневым `.prettierignore`, которого у сайта нет.

**Acceptance Criteria:**

- [ ] Каждый файл, который пишет команда ядра и побайтно сверяет гейт, либо выходит из писателя в
      форме пресета Prettier ядра, либо исключён из Prettier сайта механизмом, который ставит
      `astrum-scena install`; выбор записан в спеке истории.
- [ ] Упакованное демо после `install`, `config resolve`, `images public-init` и
      `content factcheck review` прогоняет `prettier --check .` сайта, затем `prettier --write .` —
      файлы, которые пишет ядро, не меняются, — и затем `astrum-scena check`, который проходит.
- [ ] Смена байтов файла, которую видит сайт, — ломающая по политике версий: запись в `UPGRADING.md`.

### Story 6.14: Contact handler export

_Обработчик контактной формы — публичный экспорт ядра для обёртки Pages Function сайта_

Objective:

- Delivery context: сайт с контактной формой ядра; найдено пробной сборкой 6.8, до 9.1.
- Primary outcome: обёртка формы сайта (AD-15) зовёт обработчик и охрану хоста из публичного экспорта
  ядра, без глубокого импорта.
- Why it matters: ядро рендерит форму и держит её логику в `src/lib/contact/`, но не экспортирует её;
  обёртка `functions/api/` сайта может взять её только глубоким импортом, который запрещает AD-3.

**Acceptance Criteria:**

- [ ] Точка входа пакета экспортирует обработчик формы, охрану хоста и тип окружения; снапшот
      `exports` их перечисляет.
- [ ] README ядра показывает обёртку `functions/api/contact.ts` и `_middleware.ts` сайта на этом
      экспорте; имена секретов — из `consumer-env`.
- [ ] Упакованное демо разрешает экспорт из tarball и проверяет его типами.
- [ ] Запись 6.8 в `deferred-work.md` про e2e формы остаётся открытой до деплоя сайта.

## Epic 7: Ядро, которое можно развивать

Минимальная документация ядра и процедура его расширения. **CAP:** CAP-12, CAP-13.

### Story 7.1: Core documentation

_Документация ядра — что это, подключение, публичный API, обновление_

Objective:

- Delivery context: владелец и любой, кто поднимает сайт на ядре.
- Primary outcome: по документации можно поднять и настроить демо-сайт, не читая код ядра.
- Why it matters: без этого каждый новый сайт требует раскопок в исходниках (CAP-12).

**Acceptance Criteria:**

- [ ] Документация — md-файлы на английском в репо ядра, версионируется вместе с ядром и публикуется с
      тегом релиза.
- [ ] Разделы: что такое ядро, подключение к сайту, ограниченная кастомизация (AD-3/AD-24),
      обновление по `UPGRADING.md` и порядок применения цепочки пропущенных переходов (AD-7).
- [ ] Каждый элемент публичного API из снапшотов 6.3 описан; гейт падает на недокументированном имени.
- [ ] `core init` создаёт скелет сайта: `site.yaml`, lock, однострочные `astro.config` и
      `content.config.ts`, вызов workflow ядра, `.env.example`.
- [ ] Раздел «Инфраструктура сайта»: проект хостинга, бакет R2, медиа-домен, секреты формы и
      Turnstile, раздельный деплой изображений (AD-15, ADR-0004); примеры — на демо.
- [ ] Проверка «с нуля»: агент в изолированной папке только с документацией и установленным пакетом
      создаёт сайт через `core init`, меняет конфиг, тему и одну разрешённую визуальную часть и
      собирает его; лог проверки сохранён.

### Story 7.2: Core extension procedure

_Процедура расширения ядра — путь от идеи или черновика на сайте до модуля и её обязательные проверки (манифест, снапшоты API, версия, CHANGELOG, документация)_

Objective:

- Delivery context: сопровождающий ядра (владелец) и сайты со своими фичами.
- Primary outcome: любое добавление в ядро идёт по одной описанной процедуре, и CI не пропускает
  изменение без её проверок.
- Why it matters: без процедуры фичи сайтов становятся постоянными форками или попадают в ядро без
  снапшотов, версии и документации (CAP-13, AD-4).

**Acceptance Criteria:**

- [ ] В репо ядра описана процедура: идея или черновик на сайте → запрос на расширение API → модуль
      или изменение ядра → релиз с переходом данных черновика в `UPGRADING.md`; отдельный скрипт по
      необходимости (AD-4).
- [ ] Черновик сайта живёт в пространстве `site-*` (коллекции, сегменты, i18n-ключи, секция `site:`)
      и объявлен манифестом; гейт коллизий 6.6 учитывает черновики (AD-18).
- [ ] В демо есть черновик, который проходит гейт и опирается только на публичный API.
- [ ] CI ядра отклоняет PR, меняющий публичный API без обновлённого снапшота, версии, записи
      CHANGELOG и документации.
- [ ] Шаблон PR ядра перечисляет шаги процедуры.

### Story 7.3: Skills operations guide

_Гайд по эксплуатационным skills — `docs/RUNBOOK.md` сайта становится частью документации ядра, описывает все поставляемые skills и не привязан к сайту; уточнения сайта остаются у сайта_

Objective:

- Delivery context: владелец любого сайта на ядре в повседневной работе с контентом.
- Primary outcome: один гайд в документации ядра объясняет, какой skill когда запускать и где он
  остановится для решения владельца.
- Why it matters: сейчас гайд описывает один сайт и лежит в исходном репо; второй сайт получил бы
  skills без инструкции (CAP-12, AD-13).

**Acceptance Criteria:**

- [ ] Гайд лежит в документации ядра на английском; для каждого content-ops skill описаны
      назначение, когда запускать, где он останавливается для владельца и какие команды CLI вызывает.
- [ ] Гайд не упоминает конкретный сайт; примеры — из демо.
- [ ] Гейт падает, если поставляемый skill не описан в гайде.
- [ ] Уточнения сайта лежат в `docs/` сайта по-русски и ссылаются на гайд ядра, не повторяя его.
- [ ] Уточнения из `docs/RUNBOOK.md` исходного репо, относящиеся к сайту, перенесены в репо сайта со
      ссылкой на версию гайда в ядре; исходный репо не меняется.

## Epic 8: Миграция для новых сайтов

migrate-wp не привязан к конкретному сайту и ставится только на фазу миграции. **CAP:** CAP-9. При
детализации историй 8.2 к входам добавляется `sites-inventory.md` (репо сайта).

### Story 8.1: Migrate-wp package

_migrate-wp — отдельный пакет в репо ядра, собранный из зоны `migration/` (эпик 2)_

Objective:

- Delivery context: будущие сайты, переезжающие с WordPress.
- Primary outcome: migrate-wp — отдельный пакет ядра со своими тестами, без знания конкретного сайта.
- Why it matters: сейчас миграция — часть исходного репо и годится только для него (CAP-9, AD-11).

**Acceptance Criteria:**

- [ ] migrate-wp — отдельный пакет в репо ядра со своей версией и тестами вне `check` сайта; `bin` —
      собранный JS (AD-11, AD-12).
- [ ] Рантайм ядра не импортирует migrate-wp; хелперы, нужные рантайму (managed-note-регион, свежесть
      перевода), лежат в ядре (AD-8).
- [ ] migrate-wp берёт загрузчик конфига и валидацию контента только из публичного API ядра (A2 в
      `epics-1-5-elicitation.md` репо сайта).
- [ ] Всё, что знает конкретный сайт (маппинги, decisions, errata, legacy-корпус), остаётся в репо
      сайта как данные миграции; пакет проходит гейт идентичности 6.9 (AD-22).
- [ ] Тесты пакета работают на синтетическом WP-дампе, включая загрузку `loadContentInventory`
      (запись 2.4 в `deferred-work.md`).
- [ ] Пути вывода берутся из конфига миграции сайта, а не вшиты как `data/migration/…` (запись 2.4).
- [ ] `content:import:full --check` сравнивает только при ре-bootstrap и не падает на правленом
      `src/content` (ADR-0012, запись 2.4).
- [ ] Команды CLI migrate-wp и схема конфига миграции — под снапшот-гейтами 6.3 и в документации
      ядра (7.1).
- [ ] Порядок шагов errata-процедуры ADR-0011 проверен: `content:import:full` не отвергает
      approved-перевод с протухшим `sourceDigest`, иначе шаги переставлены (запись 2.4).

### Story 8.2: Migration source adapters

_Адаптеры источника (qtranslate, одноязычный WP, WP Media Folder, zu-media, форматы записей) и конфиг миграции сайта; ни одного конкретного сайта в коде_

Objective:

- Delivery context: переезд сайтов №2 и №3, затем любого WP-сайта на теме zu.
- Primary outcome: отличия источников закрыты адаптерами, а соответствия конкретного сайта — его
  конфигом миграции.
- Why it matters: три сайта различаются языками, медиатекой и форматами записей; без адаптеров каждый
  потребовал бы форк импортёра (CAP-9, AD-11).

**Acceptance Criteria:**

- [ ] Адаптеры: qtranslate и одноязычный WP (языки), zu-media и WP Media Folder (медиатека), форматы
      записей вроде `video` (`sites-inventory.md` (репо сайта)).
- [ ] Конфиг миграции сайта задаёт соответствие категорий и измерений таксономии, пропускаемые
      страницы, подпись прав и выбор адаптеров; схема строгая.
- [ ] Каждый адаптер тестируется на своём синтетическом WP-дампе; дампы включают частичные переводы,
      пропавшие медиафайлы и неизвестные форматы записей, и импорт сообщает о каждом случае в отчёте,
      ничего не теряя молча.
- [ ] Импорт сайта №1 через адаптеры и его конфиг даёт тот же результат, что сейчас; сверка —
      локально на реальном дампе, который в репо ядра не попадает.
- [ ] В коде пакета нет имён, доменов и категорий конкретного сайта — проверяет гейт идентичности.

### Story 8.3: Migration phase install

_Установка только на фазу миграции; флаг `migration.closed` требует удалить пакет и `import-wp`_

Objective:

- Delivery context: сайт во время переезда с WP и после него.
- Primary outcome: migrate-wp и `import-wp` стоят в сайте только на фазу миграции и исчезают вместе
  со своими проверками после её закрытия.
- Why it matters: иначе миграционный код и гейты живут в сайте навсегда, а импортёр может перезаписать
  правленый контент (AD-11).

**Acceptance Criteria:**

- [ ] migrate-wp ставится обычной зависимостью, skill `import-wp` — установкой skills из 6.7; оба несут
      штамп версии, который проверяет гейт 6.8 (AD-20).
- [ ] При `migration.closed: true` гейт падает, если migrate-wp или `import-wp` всё ещё стоят; проверка
      версии migrate-wp снимается.
- [ ] После закрытия запись в `src/content` через migrate-wp невозможна — команда падает с понятной
      ошибкой.
- [ ] Данные миграции сайта (читает только импортёр) остаются в его репо; живые данные (реестр
      мастеров, factcheck-ledger) от migrate-wp не зависят (AD-9, AD-11).
- [ ] Демо проверяется в обоих режимах: открытая миграция на синтетическом дампе и закрытая.
- [ ] `import-wp` описан в гайде по skills, и гейт 7.3 его учитывает.
