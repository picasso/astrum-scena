## Intent

**Problem:** Ядро готово к открытию, но нет ни способа проверить именно то дерево, которое станет
единственным коммитом публичного репо (гейт по списку владельца и сканер секретов на этом коммите),
ни описанного порядка ручных шагов владельца. Релиз из CI на `main` по-прежнему идёт с `--dry-run`,
README говорят «not published yet», версия ядра `0.0.0`, а в публичном репо `pnpm check` у
контрибьютора без списка владельца падает (отложено из 6.9b).

**Approach:** Добавить команду, которая собирает orphan-коммит итогового дерева во временном клоне и
прогоняет на нём гейт идентичности по локальному списку и сканер секретов; записать ранбук
публикации для владельца; подготовить дерево к первому выпуску (версия ядра, README); вне CI без
списка гейт идентичности пропускается с предупреждением. Сами публикация, создание репо, trusted
publisher, архивация и снятие `--dry-run` — шаги владельца по ранбуку, не этой правки.

## Boundaries & Constraints

**Always:**

- Команда проверки дерева не трогает рабочий репо: orphan-коммит создаётся во временном клоне
  (`git clone --no-local` в scratch-каталог), ничего не пушит и печатает только вердикт и пути находок,
  не сами строки списка.
- Сканер секретов — `gitleaks` в закреплённом Docker-образе (как Playwright-образ для e2e), запуск
  `detect` по истории временного клона, то есть ровно по orphan-коммиту; без Docker команда падает с
  подсказкой.
- Ранбук — `docs/publication.md` на русском: шаги по порядку с командами, кто делает (владелец), что
  проверить после шага; без имён, доменов и путей владельца (`pnpm check:identity`).
- Тексты README, CHANGELOG и CLI — на английском.
- Решение владельца: `--dry-run` с шага `main` снимается отдельным коммитом уже в публичном репо,
  после ручной публикации и настройки trusted publisher; в этом дереве `release.yml` и guard-тест
  `scripts/release.test.ts` не меняются, а ранбук описывает тот коммит (что снять, чем заменить
  guard: шаг `main` без `--dry-run`, остальные с ним).
- Решение владельца: без списка владельца `check:identity` вне CI (переменная `CI` не задана)
  проходит с предупреждением в stderr; в CI (`CI` задан) список обязателен, как сейчас. Правило
  обновляется везде, где записано (AGENTS.md Identity, ADR и контекст эпика, если там).
- Решение владельца: до `1.0.0` версия ядра в npm — `0.<эпик>.<история>` той истории, что его
  выпускает; первая публикация — `0.6.9`, первый тег публичного репо — `v1.6.9`. Ломающий выпуск в
  `0.x` — любая более высокая версия со своим разделом в `UPGRADING.md` (не обязательно новый minor);
  сайт до `1.0.0` закрепляет версию точно. С `1.0.0` (9.3) — semver, как записано сейчас.

**Never:**

- Не публиковать в npm, не создавать и не пушить репо, не трогать настройки GitHub/npm, не
  архивировать `astrum-scena-zero` — это шаги владельца.
- Не ослаблять гейт в CI: при заданном `CI` без списка он падает, как сейчас.
- Не коммитить.

## Implementation Notes

- `scripts/publication-tree.ts`: `checkPublicationTree` получает список, сканер секретов и вывод
  явно; CLI подставляет `.identity-denylist`/`IDENTITY_DENYLIST` (через `--env-file-if-exists=.env`,
  как `check:identity`) и `dockerGitleaks`. Клон — `git clone --no-local` в `os.tmpdir()`, orphan-ветка
  `publication` из SHA `HEAD`, коммит без хуков и подписи от нейтрального имени, все прочие ссылки и
  `origin` удаляются; команда сама проверяет, что `git rev-list --all` даёт один коммит и что его
  дерево равно дереву `HEAD`. Гейт идентичности — сам `scripts/check-identity.ts` с cwd в клоне и
  списком в переменной окружения; gitleaks — `detect --source /repo --redact --exit-code 2
  --report-format json` в `ghcr.io/gitleaks/gitleaks:v8.30.1@sha256:c00b6bd0…`, клон смонтирован
  только на чтение, `safe.directory=*` передаётся через `GIT_CONFIG_*`. Из отчёта печатаются только
  `File`, `StartLine`, `RuleID`. Незакоммиченные изменения рабочего дерева — предупреждение: проверяется
  только `HEAD`.
- Тест `scripts/publication-tree.test.ts` (в `pnpm check` через `vitest`) — фикстурный репо, в истории
  и побочной ветке которого лежат строка из списка и «токен»; подменённый сканер записывает, что видит
  клон (один коммит, одна ссылка), и ловит токен в дереве. Покрыты все строки матрицы, кроме двух
  строк `check:identity` — они в `scripts/check-identity.test.ts`.
- `check:identity` без списка вне CI не пропускается целиком: общие шаблоны (домены, hex-ID)
  проверяются и валят гейт как раньше, пропускается только список владельца — с предупреждением в
  stderr. «CI задан» — переменная `CI` определена (любым значением).
- Версии `0.x`: `isBreakingBump` в `0.x` — любая более высокая `0.y.z` или `1.0.0`, `isCompatibleBump` —
  любая более высокая `0.y.z`; выбор между ними делает `UPGRADING.md` (есть раздел или
  `[Unreleased]`-записи — ломающий, нужен раздел). Форма раздела ломающего выпуска в `0.x` любая, с
  `1.0.0` — `x.0.0`. `0.0.0 → 0.6.9` проходит как совместимый (`UPGRADING.md` пуст).
- Правило «без списка» и схема версий обновлены также в `.env.example`, `ci.yml` (комментарии),
  ADR-0016 (п. 1 «Решения», «Последствия» 6.9), AGENTS.md, `epic-6-context.md`, спайне AD-7 и в
  критериях `epics.md` 6.2 и 6.3 (правило AGENTS.md о контракте закрытых историй); в 6.9 изменён
  только критерий первого тега.
- Не сделано в этой правке: живой прогон `pnpm check:publication-tree` с gitleaks — Docker-демон на
  машине не запущен. Часть без gitleaks (клон, orphan-коммит, гейт по списку владельца) прогнана на
  текущем `HEAD` с заглушкой сканера — зелёная. Не проверены вживую: вытягивание образа на arm64,
  `safe.directory` через окружение, код выхода 2 и путь отчёта gitleaks 8.30.1.
- Хук `commit-msg` (`scripts/check-commit-msg.ts`, B8) следует тому же правилу: без списка вне CI
  проверяет сообщение только по общим шаблонам и печатает предупреждение в stderr, с заданным `CI`
  (в том числе `--range` в CI) падает, как раньше.
- `check:publication-tree` запускает гейт из дерева клона (`scripts/check-identity.ts` опубликованного
  коммита), а не из рабочей копии; без него в дереве команда падает. Тест `dockerGitleaks` гоняет
  настоящий gitleaks на фикстурных клонах (токен вида GitHub PAT и чистое дерево): локально без Docker
  пропускается, с заданным `CI` без Docker падает.
- Живой прогон с Docker: тесты с настоящим gitleaks проходят. На `HEAD` gitleaks нашёл 48 ложных
  `generic-api-key` во вендорных файлах BMAD (хеши `_bmad/_config/files-manifest.csv`, учебный
  просроченный JWT в `api-testing-patterns.md` TEA). Решение владельца — узкий список исключений
  `.gitleaks.toml` (манифест целиком и одна строка `expiredToken` в файлах TEA); команда требует этот
  файл в дереве. Прогон на временном коммите рабочего дерева в отдельном клоне зелёный; на `HEAD`
  команда зелёная после коммита этих правок.
